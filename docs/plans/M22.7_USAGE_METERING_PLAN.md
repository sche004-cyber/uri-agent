## §0. Clarifications

The architecture doc (§7.1, §8, §9, §22.1) specifies the shape of usage metering and the pre-flight budget check but leaves several implementation-level decisions open. Resolving them here so Gemma doesn't have to improvise.

**0.1 — `ModelRouter._budget_ok()` becomes a real check, not another seam.** M22.6 deliberately left it as a named, always-`True` no-op (its own docstring says so explicitly: *"M22.7 wires the real usage_meter ceiling check at this exact point"*). M22.7's whole job is to fill that in. Unlike M22.6's seam, this one must be genuinely testable: with a configured ceiling and recorded usage that exceeds it, a pre-flight call must return `False` and `ModelRouter.attempt()` must advance to the next candidate exactly as it does today for an unhealthy provider (§8.3: *"blocks, ModelRouter proceeds to fallback/degrade exactly as if the provider itself were unavailable"*).

**0.2 — Ceiling configuration needs a new, small, per-user store; default is unlimited.** Nothing in the current tree stores a "monthly ceiling" anywhere. Following the exact migration discipline §20.5 already established for per-user provider config ("per-user config starts empty and inherits from it — no existing deployment's behaviour changes until a user opts into per-user config"): a new `UsageCeilingStore` (one JSON file per user, mirroring `ProviderConfigStore`'s existing file-per-user shape in `uri_core/core/provider_registry.py`) holds an optional `monthly_token_ceiling` per role (or a single account-wide ceiling — see acceptance criteria; a single account-wide ceiling is simpler and matches §8's phrasing "the user's configured monthly ceiling", singular). Absent a configured ceiling, `_budget_ok()` always returns `True` — zero behaviour change for every existing single-user install on day one, identical in spirit to §20.5.

**0.3 — Confidence labelling is mechanical, not estimated-by-default.** §8.1 requires every numeric field to carry `KNOWN|ESTIMATED|UNAVAILABLE`. `ModelResponse.prompt_tokens`/`eval_tokens` are `KNOWN` when the provider actually reported them (Ollama's real API response does); when a provider returns `None` for either, the field is recorded as `UNAVAILABLE` — **never silently estimated as if it were the real figure**. `estimate_tokens()` (already in `context_budget.py`, used for M21's oversized-prompt warning) is used only for the **pre-flight** check itself (`_budget_ok()` estimates the *upcoming* call's cost against remaining ceiling, before the call happens — the actual call hasn't produced a real count yet) — never used to backfill a completed `UsageRecord`'s `prompt_tokens`/`eval_tokens` fields after the fact. This keeps §8.1's "never fabricate a real count" rule and §8.3's "purely observational, records after a call completes" rule both true without conflating the two.

**0.4 — One `UsageRecord` per `ModelRouter.attempt()` call, not one per candidate tried.** `attempt()`'s fallback loop may try several candidates before succeeding or exhausting the chain. Recording is one append per outer `attempt()` call: on success, `outcome="success"`, the winning candidate's `provider_id`/`model`, and `fallback_from` set to the list of earlier-tried-and-skipped candidates (already computed as `tried` inside `attempt()`); on `AllProvidersUnreachableError`, one record with `outcome="unreachable"` and no token/duration figures (`UNAVAILABLE`). A `ProviderAuthenticationError` is **not** recorded as a usage event at all — it never reached a real provider call in the sense §8.1 means (no tokens were spent, no provider actually attempted the request) and recording it would misrepresent an auth failure as metered usage. Recording never happens on the health/budget pre-checks themselves (those are skips, not attempts).

**0.5 — `/usage` and `/usage/limits` are same-user-only in M22.7; no admin cross-user dashboard.** The architecture doc's own migration notes (§20) and M22.4's `CapabilityResolver` precedent both scope new surfaces to the minimum the milestone actually needs. Nothing in §8/§22.1 asks for an ADMIN-wide usage view, and building one now would be exactly the "unconsumed configuration surface" §6.5/§21 repeatedly warns against. `GET /usage` and `GET|PUT /usage/limits` operate only on the authenticated caller's own `principal.user_id`, mirroring `/providers/config`'s existing per-user scoping exactly.

If the User wants a different resolution to any of these four points, say so at ACCEPT; otherwise all four are treated as accepted defaults.

## §1. Objective

Per `URI_M22_ARCHITECTURE.md` §7.1, §8, §9, §22.1: append-only, per-user usage records for every real model call the `ModelRouter` makes; a deterministic, pre-flight (never post-hoc) monthly-ceiling budget check wired into `ModelRouter.resolve()`/`attempt()` at the exact seam M22.6 reserved; a zero-model-call dashboard aggregation over that JSONL; and two new same-user-scoped endpoints (`GET /usage`, `GET|PUT /usage/limits`) exposing it.

## §3. Scope — file by file

**NEW `uri_core/core/usage_meter.py`**
- `UsageRecord` (dataclass, frozen): `ts` (UTC ISO8601), `user_id`, `session_id: Optional[str]`, `role`, `provider_id: Optional[str]`, `model: Optional[str]`, `prompt_tokens: {"value": Optional[int], "confidence": "KNOWN"|"UNAVAILABLE"}`, `eval_tokens` (same shape), `duration_seconds: {"value": Optional[float], "confidence": "KNOWN"|"UNAVAILABLE"}`, `outcome: "success"|"unreachable"`, `fallback_from: List[str]`, `estimated_cost: {"value": None, "confidence": "UNAVAILABLE"}` (no real pricing table exists anywhere in this codebase — §21's "no unconsumed configuration surface" rule means this field is carried in the shape §8.1 specifies but is honestly `UNAVAILABLE` in M22.7, not fabricated; a real cost model is out of scope here exactly like a second provider adapter was out of scope for M21).
- `UsageMeter.record(record: UsageRecord) -> None` — append-only, one JSON line per record, to a per-user, per-calendar-month file (`uri_workspace/users/<user_id>/usage/<YYYY-MM>.jsonl`, following `user_scoped_path`'s existing convention from `server.py`). Append-only avoids the read-modify-write race §5's own security-considerations line already names as the reason for this shape. Never raises on a write failure — usage recording is observational, must never break a real model call (mirrors `_record_audit_safely`'s existing "never raises" discipline in `approval_gate.py`).
- `UsageMeter.estimate_current_month_tokens(user_id: str, role: Optional[str] = None) -> int` — a pure fold over the current month's JSONL summing `prompt_tokens.value + eval_tokens.value` wherever both are `KNOWN` (an `UNAVAILABLE` record contributes 0 — the ceiling check is necessarily conservative, never inflating usage from a guess). Used by `_budget_ok()`'s pre-flight estimate.

**NEW `uri_core/core/usage_aggregator.py`**
- `aggregate_month(user_id: str, month: Optional[str] = None) -> Dict[str, Any]` — a pure fold over one month's JSONL (defaulting to the current month) plus the static `PROVIDER_CATALOGUE` (M22.5), producing per-role and per-provider totals (`KNOWN` token sums, count of `UNAVAILABLE` records so the dashboard can say "N calls with unmeasured cost" rather than silently undercounting), call counts by `outcome`, and the configured ceiling/threshold state from `UsageCeilingStore`. **Zero model calls** — this module imports neither `ModelProvider` nor `ModelRouter` (invariant #5, §19.4), enforced by a dedicated AST-scan test exactly like `model_router.py`'s own import-boundary test from M22.6.

**NEW `uri_core/core/usage_ceiling_store.py`**
- `UsageCeilingStore(user_id)` — one JSON file per user (`uri_workspace/users/<user_id>/usage_ceiling.json`), following `ProviderConfigStore`'s exact file-per-user pattern from `provider_registry.py`. `get_ceiling() -> Optional[int]` (token count; `None` means unlimited, the default). `set_ceiling(value: Optional[int]) -> None`. `get_warn_threshold_ratio() -> float` (default `0.8`, i.e. warn at 80% of ceiling — a fixed constant like M22.6's `HEALTH_COOLDOWN_SECONDS`, not a second user-configurable knob unless the User asks for one at ACCEPT).

**MODIFY `uri_core/core/model_router.py`**
- `_budget_ok(provider_id, role, principal)` — real implementation: if `principal is None` or the principal has no configured ceiling (`UsageCeilingStore(principal.user_id).get_ceiling()` is `None`), return `True` unchanged (§0.2's zero-behaviour-change default). Otherwise, estimate this call's cost via `estimate_tokens()` against `complete_kwargs`'s `system`+`user` text (the same estimator M21 already uses), add it to `UsageMeter.estimate_current_month_tokens(principal.user_id)`, and return `False` (stop) when that sum meets or exceeds the ceiling. The **warn** threshold (§8.3's other named state) does not block — it is surfaced via the `GET /usage` response's own aggregation, not via `_budget_ok()`'s boolean, since `_budget_ok()` has no channel back to the caller besides true/false.
- `attempt()` — on a successful `provider.complete(...)` call, before returning, calls `usage_meter.record(...)` with the real `ModelResponse` fields and the `tried` chain built so far as `fallback_from`. On exhausting the chain (`AllProvidersUnreachableError`), records one `outcome="unreachable"` entry before raising. Neither `resolve()` (the observation-only variant with no real call) nor the health/budget skip-continue branches record anything — only `attempt()`'s two terminal points do.

**MODIFY `uri_core/app/server.py`**
- `GET /usage` — returns `usage_aggregator.aggregate_month(principal.user_id)` for the authenticated caller. `USER`-classified route (§19.4 invariant #6's route table), same tier as `GET /providers`.
- `GET /usage/limits` — returns the caller's current ceiling + warn-threshold-ratio from `UsageCeilingStore`.
- `PUT /usage/limits` — sets the caller's ceiling (`{"monthly_token_ceiling": int | null}`), mirroring `PUT /providers/config`'s existing request/response shape exactly.
- All three added to the route-classification table alongside the existing `/providers*` entries (§19.4 invariant #6 stays satisfied by extension, not by a new mechanism).

## §5. Security Considerations

**5.1 — No prompt/response content is ever stored.** `UsageRecord` carries only counts, durations, and outcomes (§8.1's own list) — never `system`/`user` prompt text, never `response.content`. This is enforced by construction (the dataclass has no such field) and verified by a dedicated test asserting `UsageRecord.__dataclass_fields__` never grows a content-shaped field and that `usage_meter.record()`'s call site in `model_router.py` never passes prompt/response text into it.

**5.2 — Append-only avoids read-modify-write races.** `UsageMeter.record()` only ever opens its target file in append mode and writes one line — no read-then-rewrite of the whole file, so two concurrent requests recording usage for the same user cannot corrupt or lose each other's record (the same reasoning `AuditTrail`'s existing append-only JSONL shape already relies on).

**5.3 — The pre-flight check never fabricates a ceiling breach or a false pass.** `_budget_ok()` only ever sums `KNOWN`-confidence historical tokens (§0.3) plus one `estimate_tokens()` call for the pending request — it never reads or trusts a client-supplied token count, and a principal with no configured ceiling always passes (§0.2), so this milestone cannot itself introduce a new denial-of-service surface against a user who never opted into budgeting.

**5.4 — Per-user isolation, unchanged pattern.** `UsageMeter`/`UsageCeilingStore` are constructed per `user_id`, storage paths built via the same `user_scoped_path()` helper every other M18/M21/M22 per-user store already uses — no new isolation mechanism invented, reusing the exact pattern `test_m21_file_store_isolation.py`/`test_multi_user_isolation.py` already prove correct for sibling stores. A dedicated isolation test for these two new stores follows that established pattern verbatim (per architecture doc line 430's own stated test technique).

**5.5 — `GET|PUT /usage/limits` and `GET /usage` require the same authenticated-principal boundary every other per-user endpoint requires** — no new authorization primitive; reuses `_resolve_context`'s existing principal resolution, same as `/providers*`.

## §6. Acceptance Criteria

1. A real (or faked, in tests) successful `ModelRouter.attempt()` call produces exactly one `UsageRecord` in the correct user's current-month JSONL, with `KNOWN` confidence for any field the provider actually reported and `UNAVAILABLE` for any it did not.
2. `AllProvidersUnreachableError` produces exactly one `outcome="unreachable"` record, no `UNAVAILABLE`-mislabelled-as-zero token figures.
3. A `ProviderAuthenticationError` produces zero usage records (§0.4) — verified by a dedicated test.
4. With no ceiling configured, `_budget_ok()` always returns `True` and every M22.6 acceptance criterion / test still passes completely unmodified (zero behaviour change for the default/unconfigured case).
5. With a ceiling configured and already-recorded usage at or above it, `_budget_ok()` returns `False` for that provider/role, and `ModelRouter.attempt()` correctly advances to the next candidate exactly as it does for an unhealthy provider — reproducing §8.3's stated "stop → fallback/degrade" behaviour with a real, deterministic test (not a mocked boolean).
6. `GET /usage` renders a correct dashboard aggregation from a fixture JSONL with **zero real model calls made during the test** (architecture doc's own explicit acceptance criterion for M22.7, reproduced literally).
7. `usage_aggregator.py` never imports `ModelProvider`/`ModelRouter` — invariant #5 (§19.4), AST-scan test.
8. `GET /usage`, `GET /usage/limits`, `PUT /usage/limits` are present in the route-classification table (invariant #6) as `USER`-tier, and a cross-user isolation test proves user A's request never returns or is influenced by user B's usage/ceiling data.
9. `wc -l uri_core/core/orchestrator.py` does not increase (invariant #11) — measured exactly.
10. `uri_core/core/model_router.py` still never imports `approval_gate`/`approval_store`/`dispatcher`/`capability_registry` (invariant #2, re-verified — this milestone's edits to `model_router.py` must not introduce a new violation).
11. Full existing regression suite (1,385 Python tests as of the M22.6 baseline, plus new M22.7 tests) passes; Flutter suite unaffected since §8 below declares `UI IMPACT: NONE`.
