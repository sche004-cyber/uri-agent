## 0. User Clarifications Incorporated Prior to ACCEPT

The User raised nine clarifications before accepting this plan. Each is now
a binding part of the plan below, not a side note:

1. **Capability grants are always backend-enforced; the UI is never the
   security authority.** Restated as an explicit invariant in §5.0 below,
   and already the mechanism in §3 point 4 (the authoritative check lives
   in `ApprovalGate.execute_tool`, independent of anything the UI does or
   fails to do) and §3 point 7 (the grants screen is a courtesy view; the
   backend's ADMIN check is what actually protects the write path).
2. **Role and capability grants are separate axes; ADMIN does not imply
   every capability.** Made explicit in §3 point 2 (new) and §5.0 below:
   the zero-behaviour-change migration default (full current registry)
   applies identically to every account regardless of `role`, and nothing
   in `CapabilityResolver` or the grants store reads `role` — an ADMIN's
   conversational turns are authorized purely by their own grants, exactly
   like a USER's. ADMIN's *only* extra authority is the separately
   classified `/admin/*` endpoint surface (`URI_M22_ARCHITECTURE.md`
   §4.5), never an implicit widening of what ADMIN may execute.
3. **`experience_tier` remains completely irrelevant to authorization.**
   Unchanged from the original draft (§5.3, §6.7) — restated in §5.0.
4. **Model/Brain output may propose capability use; it can never create,
   modify, grant, revoke, or elevate a grant.** New: §3 point 3(new) and
   §5.0 — no code path reachable from a Brain-proposed tool call touches
   `capability_grants.json`; the only writers of that store are the new
   ADMIN-only HTTP handlers, authenticated exactly like every other
   `/admin/*` mutation.
5. **Exact intersection model, least privilege preserved.** Quoted
   verbatim from `URI_M22_ARCHITECTURE.md` §3.2 in §3 point 1 below; this
   milestone implements the `registry_capabilities ∩ user_grants` portion
   of that formula (the `mode_allowlist`/`node_scope` terms are future,
   currently-universal identity terms, not built here — see §3's deferred
   list), and `resolved ⊆ granted ⊆ registered` is a tested invariant
   (§6.5).
6. **Every grant-mutation has an authorization boundary and audit
   evidence.** New scope item — §3 point 6 now requires
   `PUT /admin/users/{user_id}/grants` to write an audit record via the
   existing `uri_core/core/audit_trail.py` (`AuditTrail.record`), matching
   the architecture's own standing rule that "every `/admin/*` action
   writes an audit record with the acting `user_id`"
   (`URI_M22_ARCHITECTURE.md` §4.5). This was previously implied by the
   general M22.3 pattern; it is now an explicit, tested requirement (§6.11,
   §7).
7. **UI IMPACT: REQUIRED, backend remains authoritative.** Unchanged —
   the ADMIN-only grants screen is built in this milestone (§3 point 7),
   and its write path has no authority of its own.
8. **Explicit test list.** §7 below now enumerates all eight categories
   the User named, each mapped to a specific test file/case rather than
   left implicit in "a negative-authorization matrix."
9. **Scope stays limited to M22.4.** Unchanged from the original draft —
   Windows packaging, Home/Office portability, and remote backend
   deployment remain explicitly deferred (§3 "Explicitly not in scope",
   §8), not folded in here.

## 1. Objective

Close S3 from `URI_M22_ARCHITECTURE.md` §3: every user today reads the
exact same capability set from the single, install-wide
`CapabilityRegistry` — there is no structure that can answer "may *this*
user use *this* capability." M22.4 makes per-user capability authority
real, concretely enforced, and administrable, not merely a data field
nobody reads.

This is the last of the four milestones `URI_M22_ARCHITECTURE.md` §17.4
flags as carrying genuinely new security surface (auth → M22.2, network
exposure → M22.3, authorization → **M22.4**, secrets → M22.5) and
therefore the last one requiring independent deep architecture review
before merge.

- M22.2 (`34839ce`): `ROLE_USER`/`ROLE_ADMIN`, `PrincipalContext`,

## 3. Scope

**In scope:**
1. **`uri_core/core/capability_resolver.py`** (new) — the extracted
   `_executable_capability_ids` logic from `orchestrator.py`
   (`URI_M22_ARCHITECTURE.md` §3.4, §17.3), plus:
   ```
   CapabilityResolver.resolve(principal) -> List[CapabilityDescriptor]
   CapabilityResolver.is_allowed(capability_id, principal) -> bool
   ```
   computed against the exact model `URI_M22_ARCHITECTURE.md` §3.2
   defines:
   ```
   resolved = registry_capabilities ∩ user_grants[principal.user_id]
              ∩ mode_allowlist[principal.mode] ∩ node_scope[principal.node_id]
   ```
   — an intersection, never a union, so every term can only narrow.
   M22.4 implements the first two terms; `mode_allowlist`/`node_scope`
   are M22.8/future seams (`URI_M22_ARCHITECTURE.md` §12.4, §16.1) and
   are treated as the universal/identity set here — present in the
   formula's shape so a later milestone adds real narrowing without
   changing this milestone's contract, not evaluated to anything
   restrictive by M22.4 itself. Least privilege is the tested invariant
   `resolved ⊆ granted ⊆ registered` (§6.5) — grants and mode/node terms
   can only ever remove capabilities, never add ones the registry
   doesn't have.
2. **`role` and capability grants are separate, non-interacting axes.**
   `capability_resolver.py` and `capability_grants.json` never read
   `PrincipalContext.role`. The zero-behaviour-change migration default
   (point 3 below) applies identically to every account regardless of
   role — an ADMIN account is not granted anything a USER account
   isn't, purely by virtue of being ADMIN. ADMIN's only extra authority
   is the separately classified `/admin/*` endpoint surface
   (`URI_M22_ARCHITECTURE.md` §4.5); it is never an implicit widening of
   which capabilities an ADMIN's own conversational turns may execute.
3. **`capability_grants.json`** (new INSTALL-scope store,
   `user_id → [capability_id]`), with a migration defaulting every
   existing/new user to the **full current registry** — this is what
   keeps M22.4 zero-behaviour-change for every existing single-user
   install on day one; grants only ever narrow behaviour once an ADMIN
   deliberately edits them. This store has exactly two writers: the
   migration itself, and the new
   `PUT /admin/users/{user_id}/grants` handler (point 6 below) — no
   Brain-proposed tool call, capability execution, or any other
   orchestrator-reachable code path may write to it. A model/Brain
   output may *propose* using a capability; it has no code path capable
   of creating, modifying, granting, revoking, or elevating a grant.
4. **Two consultation points** (`URI_M22_ARCHITECTURE.md` §3.3):
   - **Advisory** — `orchestrator._build_query_context` calls
     `CapabilityResolver.resolve` so the Brain is never even offered a
     capability the calling user cannot use.
   - **Authoritative** — `ApprovalGate.execute_tool` calls
     `CapabilityResolver.is_allowed` immediately before the existing
     `capability_registry.describe_status` lookup, so a stale
     catalogue, a race, or a bug in the advisory path can never become
     an execution path. Both consultation points are **read-only**
     calls (`resolve`/`is_allowed`); neither the Brain nor any code on
     this path can reach a write to `capability_grants.json` — a model
     may only ever propose a capability use that is then checked
     against grants it cannot alter.
5. **`orchestrator.py`**: net-neutral-or-negative edit only — the
   extraction moves logic out, it does not add new orchestration
   behaviour. `wc -l orchestrator.py` must not increase (the standing
   M22-onward rule).
6. **`server.py`**: `/capabilities` becomes principal-aware (returns
   the resolved, not raw, catalogue). New ADMIN-only grant-management
   endpoints, reusing M22.3's exact classification/dependency pattern:
   - `GET /admin/users` — list accounts (for the grants UI's picker).
   - `GET /admin/users/{user_id}/grants` — a user's current grants.
   - `PUT /admin/users/{user_id}/grants` — replace a user's grant set
     (validated against the live registry; rejects unknown
     capability_ids rather than silently dropping them). On success,
     writes an audit record via the existing
     `uri_core/core/audit_trail.py` (`AuditTrail.record`) capturing the
     acting ADMIN's `user_id`, the target `user_id`, and the resulting
     grant set — the same standing requirement
     `URI_M22_ARCHITECTURE.md` §4.5 already states for every
     `/admin/*` action, made concrete and tested for this endpoint
     specifically (§6.11, §7).
   All new routes added to `route_classification.py` in the same
   commit that adds them — the enumeration test must never see an
   unclassified route, even transiently.
7. **`uri_ui/`** (UI IMPACT: REQUIRED, not deferred) — a new
   ADMIN-only Capability Grants screen (Settings → Admin, visible only
   when `AccountInfo.isAdmin`, mirroring the M22.3
   `connections_screen.dart` pattern of a real backend check backing a
   UI courtesy, never the reverse): lists accounts, shows each
   account's current grant set against the full registry, lets an
   ADMIN toggle individual capabilities per user. Read-only for a
   non-admin viewer (in the unlikely case the route is reached without
   the nav gate); the backend's own ADMIN check is what actually
   protects the write path, exactly as M22.3 established. The screen
   has no local notion of "allowed" — every toggle is an optimistic UI
   state that is reverted if the backend `PUT` rejects it; the UI never
   decides authorization itself.
8. **Tests**: unit tests for `CapabilityResolver`'s intersection logic
   (including the "grants narrow, registry is the ceiling" invariant);
   integration tests proving a capability outside a user's grants is
   both absent from `/capabilities`'s resolved view *and* rejected by
   `ApprovalGate.execute_tool` if invoked directly (the authoritative
   check must not be provable-bypassable by skipping the advisory
   one); a negative-authorization matrix for the three new ADMIN
   endpoints (401/403/success, same shape as
   `test_m22_3_route_authorization.py`); a migration test proving
   every pre-existing user defaults to the full registry; a Flutter
   widget test for the new grants screen (admin sees it and can toggle
   a grant against a mock backend; non-admin does not see the nav
   entry). See §7 for the full, explicitly enumerated test list.

## 5. Security Considerations

### 5.0 Invariants (User-mandated, binding)

These four are restatements of the User's clarifications 1, 2, 3, and 4
as concrete, code-level invariants — every subsequent numbered item
below is a mechanism that enforces one of these, not a separate idea:

- **Backend-enforced only.** No UI state, UI-side check, or UI-computed
  value ever decides whether a capability executes. The Flutter grants
  screen and the resolved `/capabilities` view are both read-outs of a
  decision the backend already made, never inputs to that decision.
- **Role ≠ grants.** `role` (`USER`/`ADMIN`) and per-user capability
  grants are independent axes. ADMIN status never implies, defaults to,
  or auto-expands a capability grant set; ADMIN's extra authority is
  scoped strictly to the `/admin/*` endpoint surface.
- **`experience_tier` is authorization-inert.** `BASIC`/`ADVANCED` is
  read in exactly one place in the entire codebase (client-facing UI
  shaping, `URI_M22_ARCHITECTURE.md` §4.4) and nowhere in
  `CapabilityResolver`, `ApprovalGate`, or any `/admin/*` handler.
- **Brain proposes, never grants.** A model/Brain output can propose
  the use of a capability; the only two writers of
  `capability_grants.json` are the one-time migration and the
  authenticated ADMIN `PUT` handler. No orchestrator- or Brain-reachable
  code path can create, modify, grant, revoke, or elevate a grant.

### 5.1 Mechanisms

1. The authoritative check lives in `ApprovalGate.execute_tool`, not
   only in the advisory catalogue-building path — an attacker (or a
   buggy Brain proposal) that never consults `/capabilities` at all
   still cannot execute an ungranted capability. This is also what
   makes "backend-enforced only" true even if the UI were compromised,
   buggy, or bypassed entirely: the UI has no channel to `ApprovalGate`
   other than the same HTTP surface any other client would use.
2. `capability_resolver.py` never imports `ModelProvider`/
   `ModelRouter` (authority must never see provider identity —
   `URI_M22_ARCHITECTURE.md` §18.1 invariant 1).
3. No authorization-reachable code path in this milestone references
   `experience_tier` — extend
   `test_experience_tier_never_authorizes.py`'s AST scan to also walk
   `capability_resolver.py` and the three new `/admin/*` handlers.
4. Grants narrow, never widen, beyond the registry:
   `resolved ⊆ granted ⊆ registered`, enforced as a test, not merely
   asserted in code comments.
5. The new grant-management endpoints are ADMIN-only using M22.3's
   exact `_resolve_admin_principal` dependency — no new authorization
   primitive is invented. Nothing in that dependency, or anywhere else
   in this milestone's diff, branches on `role == ADMIN` to widen a
   *conversational* capability grant — `_resolve_admin_principal` gates
   the `/admin/*` HTTP surface only, never `CapabilityResolver`'s
   output for that same ADMIN's own turns.
6. `PUT /admin/users/{user_id}/grants` validates every submitted
   capability_id against the live registry and rejects the whole
   request (never partially applies) if any id is unknown — an ADMIN
   typo must not silently grant nothing while appearing to succeed.
7. Zero-behaviour-change migration (§3, point 3) is itself a security
   property: a single-user install's existing behavior does not
   silently narrow the day this ships, and it applies identically to
   USER and ADMIN accounts (no role-conditioned migration logic).
8. `PUT /admin/users/{user_id}/grants` writes an audit record (acting
   `user_id`, target `user_id`, resulting grant set) via the existing
   `AuditTrail.record`, satisfying `URI_M22_ARCHITECTURE.md` §4.5's
   standing "every `/admin/*` action writes an audit record" rule for
   this specific mutation, and proven by test (§7), not left implicit.
9. No code path reachable from a Brain-proposed tool call (i.e.
   anything downstream of a model's tool-use output, including
   `ApprovalGate.execute_tool` itself) can reach a write to
   `capability_grants.json` — verified by the same kind of reachability
   check the `experience_tier` AST scan already performs, applied to
   the grants store's writer functions instead.

## 6. Acceptance Criteria

1. `CapabilityResolver.resolve`/`is_allowed` are pure, testable
   functions of `(registry, grants, principal)` with no FastAPI/HTTP
   dependency — the same separation `authorization.py` established in
   M22.3.
2. A capability outside a user's grants is absent from that user's
   `/capabilities` response AND rejected (not merely hidden) if
   `ApprovalGate.execute_tool` is invoked for it directly.
3. `GET/PUT /admin/users/{user_id}/grants` and `GET /admin/users`:
   401 anonymous, 403 non-admin, success ADMIN-only.
4. Every pre-existing user_id defaults to the full current registry at
   migration time — proven by a migration test, not asserted.
5. `resolved ⊆ granted ⊆ registered` holds as a tested invariant.
6. `wc -l uri_core/core/orchestrator.py` does not increase versus the
   M22.3 baseline.
7. No authorization-reachable code in this milestone's diff references
   `experience_tier` (AST-scan test, extended from M22.3's).
8. The Flutter grants screen: an ADMIN account sees it and can toggle
   a grant against a mock backend; a non-admin account does not see
   the nav entry; both proven by `flutter test`, not by inspection.
9. Full regression: backend suite stays ≥ 1,218 (M22.3 baseline) plus
   this milestone's new tests, zero collection errors; Flutter suite
   stays ≥ 103 plus this milestone's new tests; `flutter analyze`
   introduces no new errors or warnings (the 8 pre-existing info-level
   lints noted at M22.3 verification are not this milestone's to fix
   unless trivially touched in a file already being edited).
10. No file outside §3/§4's list is touched.
11. `PUT /admin/users/{user_id}/grants` produces exactly one audit
    record per successful call, containing the acting admin's
    `user_id`, the target `user_id`, and the resulting grant set —
    proven by querying `AuditTrail` in the test, not by log inspection.
12. Two ADMIN accounts, each with their own restricted grant set,
    each resolve only their own grants — proven by a per-user isolation
    test (one admin's grants never leak into another admin's or
    another user's resolved view).

## 7. Test Plan

Mirrors M22.3's approach for fixtures and structure
(`test_m22_3_route_authorization.py`'s pattern, including
`edge.reset_rate_limiters()` in `setUp`/`tearDown`, since the new
`/admin/*` routes sit behind the same rate-limited `/auth/*` login flow
the fixture already signs in through). The User's eight named test
categories map onto these files/cases explicitly, so none is left
implicit inside a general "negative-authorization matrix" description:

`test_m22_4_capability_resolver.py`:
1. **Least privilege / intersection behavior** — `resolved ⊆ granted
   ⊆ registered` as a property test across generated registry/grant
   combinations, plus the specific "grants narrow, registry is the
   ceiling" case.
2. **`experience_tier` never affects grants** — extends
   `test_experience_tier_never_authorizes.py`'s AST scan to
   `capability_resolver.py` and the three new `/admin/*` handlers
   (also satisfies §6.7).
3. **Model proposals never create grants** — a reachability/AST check
   that no function reachable from `ApprovalGate.execute_tool` (the
   Brain-proposal execution path) can reach a write to
   `capability_grants.json`; plus a behavioral test that proposing an
   ungranted capability through `ApprovalGate.execute_tool` is rejected
   and leaves the grants store byte-for-byte unchanged.

`test_m22_4_grant_endpoints.py`:
4. **Unauthorized USER attempts** — an authenticated non-admin USER
   gets 403 on all three `/admin/*` grant endpoints.
5. **Unauthorized anonymous attempts** — no session/token gets 401 on
   all three endpoints.
6. **ADMIN grant/revoke** — an authenticated ADMIN can `PUT` a
   narrower grant set and a wider one (up to the registry ceiling);
   both are reflected in a subsequent `GET` and in that user's
   resolved `/capabilities`.
7. **Per-user isolation** — granting/revoking user A's capabilities
   does not change user B's stored grants or resolved view (also
   §6.12).
8. **Migration default** — every pre-existing `user_id` defaults to
   the full current registry at migration time, for both USER and
   ADMIN accounts identically (also proves clarification 2: the
   migration is role-blind).
9. **Audit evidence** — a successful `PUT` produces exactly one
   `AuditTrail` record with the acting admin, target user, and
   resulting grants (also §6.11).
10. **UI cannot bypass backend authorization** — an integration test
    that calls `ApprovalGate.execute_tool` directly for a capability
    absent from the caller's grants (i.e. simulating a client that
    skips the advisory `/capabilities` read the UI normally performs)
    and asserts rejection — proving the authoritative check does not
    depend on any UI-side gate having run first.

`m22_4_capability_grants_test.dart` (new file in `uri_ui/test/`, not
folded into `m22_ui_parity_test.dart`):
11. An ADMIN account sees the grants screen and can toggle a grant
    against a mocked backend, with the toggle reverting if the mocked
    backend returns a rejection (proving the UI treats the backend
    response as authoritative, not its own toggle state).
12. A non-admin account does not see the nav entry to the screen at
    all.

## 8. Recommended Next Milestone (not this one, not planned in detail
here)

The User has set a standing product direction for every milestone from
here on: UI is first-class, portable across Home/Office/Custom
environments, no environment-specific configuration hardcoded into the
UI, URI should ultimately be an installable Windows application, both
local and remote backend modes should be supported, and development
tooling stays separate from the installed product. M22.4 is designed
not to conflict with that direction (its new admin screen adds no
hardcoded environment assumption, and reuses `uri_ui/`'s existing
backend-address configuration seam rather than duplicating it), but it
does not itself deliver that direction — CapabilityResolver is
authorization work, not packaging work, and folding both into one
milestone would blur two different risk profiles (a security-surface
milestone and a build/distribution milestone).

The milestone immediately after M22.4 should be a dedicated
**Portability & Packaging Foundation** milestone: an explicit
local-vs-remote backend connection mode in the UI with no hardcoded
default, a real Windows installer/package for the already-scaffolded
`uri_ui/windows/` desktop target, and an explicit boundary separating
development tooling (`scripts/qwen_coordinator*.py`,
`ORCHESTRATION.md`-related orchestration scripts, this repository's own
test/dev dependencies) from whatever actually ships inside that
installer. That milestone is deliberately not scoped here — it needs
its own Claude-drafted plan, at the point M22.4 is verified and this
repository's state is re-inspected, per AO-4's own "never repeat the
previous plan" rule (`ORCHESTRATION.md` §1.1 step 7).
