**Status:** DRAFT — for User review and authorization. No implementation has

## 1. Acceptance Criteria for This Plan

This plan is acceptable only if it:

1. Defines a **frozen visual contract** precise enough that two different
   implementers would produce pixel-equivalent output from it.
2. Defines a **machine-readable design manifest** format so the contract is
   enforceable by code, not just prose.
3. Defines a **presentation-state contract** covering loading/live/
   unavailable states so honesty about data never forces a different
   layout shape than the approved one.
4. Gives every legacy widget a disposition (done in the audit, §5) and
   carries it through into concrete task steps here.
5. Gives every companion tool a BUILD NOW/DEFER decision (done in the audit,
   §6) and only schedules BUILD NOW tools as prototype work.
6. Defines real, automatable visual QA: geometry assertions, golden/
   reference comparison, a diff artifact, a numeric perceptual threshold,
   and an explicit human sign-off step that code cannot substitute for.
7. Defines a region-by-region loop (review → implement → render → compare →
   repair → repeat) with a stop condition per region, not an open-ended
   iteration.
8. States explicitly what remains unauthorized until the User approves this
   plan.

## 2. Frozen Visual Contract

The contract is: **`docs/design_references/dashboard_preview.html` at its
native 1024×682 aspect ratio is the single source of visual truth for the
approved desktop dashboard.** Nothing in the Flutter implementation may
introduce a value (color, size, radius, spacing, font) for an in-scope
region that is not traceable to this file or to the design manifest derived
from it. Where Flutter cannot express something 1:1 (e.g. `cqw` container
units, CSS blend modes, or `clip-path` polygons), the manifest must record
the intended *effect* (exact pixel value at 1024×682, plus the scaling
rule) so an implementer never has to guess.

Regions in scope, each independently frozen (matches the audit's region
boundaries in §4.1):

1. Left rail: fixed width proportion, raster logo block, caption, 13-item
   nav (no additions), forest-photo footer with quote + org/version line.
2. Hero: forest photo, gradient overlay, greeting text block, quote block.
3. Tabs row: 7 pills, one active state.
4. Metrics row: 5 equal cards (CPU/GPU/RAM/Disk + System Health), each
   card's internal layout, filled sparkline treatment, and unavailable-state
   variant (see §3).
5. Secondary panels row: Activity, Model Usage, Storage, Active Connections
   — same rule.
6. Composer + tip line: icon set (including the right-arrow send icon),
   sizing, glow, tip copy slot.
7. Right rail: window controls, profile row, date, 4 operational cards.

**Freeze rule:** once a region's manifest entry is accepted (§4 loop, step
"repair"), it cannot be changed except through the same review loop — no ad
hoc tweaks during unrelated work. This is what "frozen" means operationally.

## 3. Machine-Readable Design Manifest

A single JSON file, `docs/design_references/dashboard_manifest.json`,
generated once from `dashboard_preview.html` and the reference PNG, and
treated as the contract's executable form. Structure:

```json
{
  "board": { "nativeWidth": 1024, "nativeHeight": 682, "columns": [0.14, 0.66, 0.20] },
  "tokens": {
    "bg": "#020910", "panel": "rgba(6,20,33,0.9)", "line": "#15334a",
    "text": "#eaf6ff", "muted": "#9bb2c4",
    "blue": "#27c9ff", "green": "#25e5aa", "pink": "#e15cf5", "gold": "#ffc437"
  },
  "regions": {
    "leftRail": { "widthFraction": 0.14, "logo": {"asset": "uri_app_logo_refined_v2.png", "scale": 1.08, "blend": "screen"}, "navItems": ["Home","Chat","Email","Drive","Files","Tasks","Calendar","Graph","Memory","Insights","Model","Tools & Skills","Settings"] },
    "hero": { "heightPx": 84 },
    "tabs": { "heightPx": 27 },
    "metrics": { "heightPx": 145, "cards": ["cpu","gpu","ram","disk","health"] },
    "panels": { "heightPx": 176, "cards": ["activity","modelUsage","storage","connections"] },
    "composer": { "heightPx": 49, "sendIcon": "arrow-right" },
    "rightRail": { "widthFraction": 0.20, "cards": ["glance","currentModel","sandbox","toolsSkills"] }
  }
}
```

(Pixel values above are illustrative placeholders for the shape of the
schema; the real manifest must be generated by measuring the actual `cqw`
values in `dashboard_preview.html` against the 1024×682 native size, not
retyped by hand from memory. That generation is task 1 of the implementation
work, below.)

**Enforcement:** a small Dart constants file,
`uri_ui/lib/theme/dashboard_manifest.dart`, is generated (or hand-synced,
with a test that fails if it drifts) from this JSON, and the dashboard
widgets read only from it — not from ad hoc literals in
`reference_dashboard.dart` or `uri_theme.dart`. This is what closes the
audit's "two color-token authorities" root cause (§4.2 item 2 of the audit).

## 4. Presentation-State Contract

Every card in scope has exactly three presentation states, and **all three
must render at the same geometry** (same card bounds, same internal grid,
same chart bounding box):

| State | Rule |
|---|---|
| `loading` | Same card shape as `live`, content replaced with a low-opacity skeleton of the *same* chart/list shape (e.g. a flat-line sparkline placeholder, not an empty card). No layout shift when it resolves. |
| `live` | Real data, filled sparkline/donut/bars exactly as the reference renders them, using real values from the wired backend call. |
| `unavailable` | Same card shape as `live`. The chart element is still drawn (e.g. the donut ring, the sparkline baseline) in a neutral/desaturated variant of its token color, with a single explicit label (e.g. "Not reported", "GPU telemetry unavailable") placed where the reference places its caption/device text — never a dash-only card, never a hollow/absent chart shape. This directly fixes the audit's confirmed regression (§4.1 of the audit: hollow donut, dash rows, missing sparkline shape).

This contract is what lets the repository's honest-data principle
(`docs/plans/M26_DASHBOARD_DESIGN_SPECIFICATION.md`) coexist with the
approved visual: **never invent a number, but never let "we don't have a
number" change the card's geometry either.**

Per-card mapping to real backend support (from the audit's §6 triage):

| Card | Live source | Unavailable trigger |
|---|---|---|
| CPU / RAM / Disk | `system_performance.py` (already wired) | request failure or platform gap |
| GPU | none exists | always `unavailable` until backend GPU telemetry ships (DEFER, per audit §6) |
| System Health | `system_performance.py` fields actually returned | any field the backend does not populate |
| Activity | `/activity` (already wired) | request failure |
| Model Usage donut | none exists | always `unavailable` until a backend request-accounting feature ships (DEFER, per audit §6) |
| Active Connections | existing connections state | per-connection, not per-card |
| Today at a glance — unread emails | `gmail_search_service.get_unread_count()` (exists, **not yet wired to `AppState`** — this is new wiring, not new backend work) | auth/API failure |
| Today at a glance — tasks/events | existing tasks/calendar state if present; confirm before wiring | absent source |

## 6. Visual QA Definition

Four layers, all required — no layer substitutes for another:

1. **Geometry assertions (automated, every CI run).** Widget tests that
   pump each card in `loading`/`live`/`unavailable` state and assert the
   outer `RenderBox.size` and key internal child offsets are identical
   across all three states, per the presentation-state contract (§4). Fails
   fast on any regression that changes a card's shape based on data
   availability.
2. **Golden/reference comparison (automated, every CI run).** Extend
   `reference_render_test.dart` to render the dashboard at exactly
   1024×682 (matching the manifest's native board size, not the current
   1440×920 arbitrary test viewport) and compare it pixel-by-pixel against
   `approved_ui_reference.png` using Flutter's `matchesGoldenFile` (or an
   equivalent deterministic comparator) region-by-region (one golden per
   region from §2, not one giant whole-board golden, so a single region's
   drift does not fail unrelated regions and does not require re-approving
   the whole board for a one-region fix).
3. **Diff output (automated artifact, not just pass/fail).** On any
   mismatch, write a difference image (e.g. a per-pixel delta heatmap) to
   `.tmp_ui_qa/<region>_diff.png` alongside the actual and expected images,
   so a human reviewer never has to reproduce the render locally to see
   what changed.
4. **Perceptual threshold (automated gate).** A numeric tolerance (e.g. a
   percentage of differing pixels above a per-channel delta, or an SSIM/
   perceptual-hash score) below which a render is accepted automatically,
   above which it requires human sign-off. The exact threshold is chosen
   during task 1 (manifest generation) by measuring the natural
   font/anti-aliasing noise floor between two renders of the *same* known-
   good state, so the gate does not chase sub-pixel rendering noise.
5. **Human visual sign-off (manual, required before any region is marked
   frozen/accepted).** No region in §2 is marked complete in this plan's
   tracking state until the User has visually confirmed it against the
   approved reference — matching the User's explicit live-verification
   preference recorded in this project's standing process (Claude audits
   for bugs/fixes after the User's own confirmation, per the 2026-09-12
   live-verification gate revision). Passing layers 1–4 is necessary but
   not sufficient to call a region done.

## 7. Region-by-Region Prototype Loop

Applied once per region from §2, in this order (rail/brand → hero/tabs →
metrics → secondary panels → right rail → composer — matching the
dependency order: the board container and tokens must exist before any
card can be measured against them):

```
1. Claude review   — confirm the region's manifest entry is complete and
                      unambiguous (no missing token, no unresolved cqw
                      value) before any code is written.
2. Implementation   — routed per AO-4 rules (Codex for the architectural/
                      multi-file steps such as the fixed-board container;
                      Gemma for bounded, single-widget token substitutions).
3. Render           — `reference_render_test.dart` produces the region's
                      screenshot at native 1024x682 scale.
4. Compare          — golden diff (§6 layers 2-4) runs against the region's
                      approved crop.
5. Repair           — any failing layer is fixed and steps 3-4 repeat
                      before moving on; Claude performs the repair directly
                      only if it is a bounded, in-scope defect found during
                      its own audit of that region (per Claude's standing
                      bounded-fix authority) — otherwise it is routed back
                      through Antigravity to the implementer.
6. Human sign-off   — User visually confirms the region (§6 layer 5) before
                      it is marked frozen. On rejection, the same loop
                      repeats with the User's specific feedback folded into
                      step 1's review, not a blind retry.
```

**Stop condition per region:** all four automated QA layers pass AND the
User has signed off. A region does not block the next region's
implementation from starting, but a region's automated tests must stay
green in CI once frozen — a later region's change that breaks an earlier
region's golden is treated as a regression, not an acceptable tradeoff.

## 8. Scope Boundaries (what this plan explicitly does NOT do)

- Does not build GPU telemetry or model-usage accounting backends (DEFER
  per audit §6) — those are separate, User-scoped backend milestones.
- Does not change the honest-data/no-fabricated-telemetry principle from
  `docs/plans/M26_DASHBOARD_DESIGN_SPECIFICATION.md` — the
  presentation-state contract (§4) is designed to satisfy both that
  principle and the approved visual simultaneously, not to override either.
- Does not authorize deleting `uri_wordmark.dart` outright — only retiring
  its use on the dashboard route, pending the call-site check in §5.
- Does not implement anything itself. This is a plan document.
