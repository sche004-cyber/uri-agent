## §0. Clarifications

**0.1 — `mode` and `experience_tier` are two different axes; this milestone must not conflate them.** The architecture doc's M22.8 entry bundles two named things under one objective, but the codebase already treats them as structurally distinct, and the pinned standing rule (`URI_M22_ARCHITECTURE.md` §4.4, enforced today by `test_experience_tier_never_authorizes.py`) is explicit: *"No authorization path may read `experience_tier`."*
- **`experience_tier`** (`BASIC`/`ADVANCED`) already exists — `user_accounts.py`, `GET /auth/me`, `POST /auth/experience-tier`, and Flutter already read/write it. It is a **zero-authority UI-detail preference only**: "how much jargon/detail is shown," never "what is callable." M22.8's "plain-language guidance"/"BASIC provider UI never shows the words 'token' or 'context window'" work is a **client-only, presentation-layer** change plus (if needed) a thin server-side wording/shape adjustment — it must never touch `CapabilityResolver`, `ApprovalGate`, `ToolDispatcher`, `CapabilityPlanner`, or `orchestrator.py`'s authorization path, exactly as the existing AST-boundary test already enforces and will continue to enforce unmodified.
- **`mode`** (`office`/`diagnostic`/`admin`) is genuinely new in M22.8: an actual **capability-filtering** axis, added as a real field on `PrincipalContext` (currently `user_id`/`role`/`device_id` only — confirmed by direct read) and wired into `CapabilityResolver.resolve()`'s existing formula. `capability_resolver.py`'s own docstring and code *already state* the full formula — `resolved = registry ∩ grants ∩ mode_allowlist[principal.mode] ∩ node_scope[principal.node_id]` — but the actual `resolve()`/`is_allowed()` implementations only ever compute `registry_ids & user_grants` today; `mode_allowlist` is not applied anywhere (confirmed by direct read — no `mode` term appears in the real intersection logic). M22.8's real job is filling in that already-declared-but-unimplemented term, not inventing a new formula.

**0.2 — `mode` narrows what `CapabilityResolver` returns; it must never be checked by `orchestrator.py` itself.** Per §17.3 (verified): `orchestrator.py` already delegates capability-catalogue assembly to the M22.4 extraction seam (`_executable_capability_ids`/`_build_query_context`'s catalogue-building, now living in `capability_resolver.py`'s intersection). M22.8 "reuses" that seam by having `CapabilityResolver.resolve()`/`is_allowed()` additionally intersect against `mode_allowlist[principal.mode]` — a change entirely inside `capability_resolver.py`, with `orchestrator.py`'s own call sites unchanged (they already just consult the resolver's output). This is why the architecture doc calls the `orchestrator.py` edit "net-neutral" — there should be none beyond what threading `principal.mode` through an already-existing `principal` parameter requires, if even that.

**0.3 — `modes.json` default set and shape.** Mirroring `institutional_rules.py`'s exact "packaged defaults, deep-merged with an optional deployment JSON override" pattern (confirmed by direct read of that module): three packaged default modes, `office` (the existing full registry — zero-behaviour-change default for every current single-mode install), `diagnostic` (a narrower allowlist: read-only/status-reporting capabilities only — e.g. `list_tasks`, `read_history`, `list_files`, `list_memory`, `view_usage`-shaped capabilities, no drafting/execution capabilities), and `admin` (the full registry, mirroring `office` — `mode` is orthogonal to `role`; an ADMIN-role user still narrows by mode like anyone else, per §0.1's "role is completely separate" line already in `capability_resolver.py`'s own docstring). A user's current `mode` is a new field alongside `experience_tier` on the account record (same file-store pattern), defaulting to `office` so no existing account's resolved capability set changes until a user (or an ADMIN, for another user) deliberately switches mode.

**0.4 — "Ceiling-reached flow" consumes M22.7's `GET /usage` shape as-is; no new backend field is invented.** M22.7's `aggregate_month()` already returns `limits: {monthly_token_ceiling, warn_threshold_ratio, warning, ceiling_reached}` (confirmed by direct read). M22.8's ceiling-reached flow is a **client-only** consumer of that already-shipped, already-tested shape — polling/reading `GET /usage` and presenting `warning`/`ceiling_reached` states in plain language. No change to `usage_aggregator.py`/`usage_meter.py`/`model_router.py` is in scope here.

If the User wants a different resolution to any of these four points, say so at ACCEPT; otherwise all four are treated as accepted defaults.

## §3. Scope — file by file

**NEW `uri_core/config/modes.py`**
- `DEFAULT_MODES: Dict[str, List[str]]` — `{"office": [...all current registry capability ids...], "diagnostic": [<read-only capability ids>], "admin": [...same as office...]}`, following `institutional_rules.py`'s exact packaged-defaults-plus-optional-`uri_workspace/modes.json`-override pattern (new module, not reusing `institutional_rules.py` itself — different domain, same pattern).
- `load_modes(path=MODES_PATH) -> Dict[str, List[str]]` — deep-merged defaults + override, never raises (degrades to defaults on missing/malformed file), mirroring `load_institutional_rules()`/`load_model_roles()`'s exact discipline.
- `VALID_MODES = {"office", "diagnostic", "admin"}`; `DEFAULT_MODE = "office"`.

**MODIFY `uri_core/core/principal_context.py`**
- Add `mode: Optional[str]` field (default `None` at the dataclass level; `server.py`'s `_resolve_principal` resolves it to the account's stored mode or `DEFAULT_MODE` — never guessed/defaulted to a privileged value, exactly matching the existing `role` field's own documented discipline in this same class).

**MODIFY `uri_core/core/user_accounts.py`**
- Add `mode: str = DEFAULT_MODE` to the account record (same migration pattern as `experience_tier`: existing pre-M22.8 accounts get the default on next load, zero-behaviour-change). A `set_mode(user_id, mode)` method mirroring `set_experience_tier`'s exact shape (self-scoped only — a user sets their own mode; an ADMIN may set another user's mode via the existing `/admin/users/{user_id}` pattern established in M22.4, not a new authority mechanism).

**MODIFY `uri_core/core/capability_resolver.py`**
- `CapabilityResolver.resolve()`/`is_allowed()`: add the `mode_allowlist[principal.mode]` intersection to the already-declared formula — `allowed_ids = registry_ids & user_grants & mode_allowed_ids` where `mode_allowed_ids = set(load_modes().get(principal.mode or DEFAULT_MODE, load_modes()[DEFAULT_MODE]))`. This is the one place `mode` is ever consulted for authorization — never `orchestrator.py`, never `ApprovalGate` directly (it already only calls `CapabilityResolver.is_allowed()`, unchanged call shape).
- `node_scope[principal.node_id]` stays an identity/universal-set no-op in M22.8 (no `node_id`/multi-node concept exists yet, per architecture doc §12.4/§21 — not this milestone's scope; naming it explicitly here so it isn't silently assumed built).

**MODIFY `uri_core/app/server.py`**
- `GET /modes` — returns the caller's current `mode` plus the full `VALID_MODES` list (for the client to render a picker) — `USER`-tier, same-user-only.
- `PUT /modes` — `{"mode": "office"|"diagnostic"|"admin"}`, self-scoped (mirrors `POST /auth/experience-tier`'s exact shape/pattern), rejects an unknown mode with 422 rather than silently defaulting.
- `_resolve_principal` threads the account's stored `mode` into the constructed `PrincipalContext` (one additional field read, same call site that already reads `role`).
- Both routes added to `route_classification.py`'s table as `USER`.

**MODIFY `uri_ui/lib/...` (client, `UI IMPACT: REQUIRED`)**
- A `mode` picker consuming `GET/PUT /modes`, presented plainly (no capability-catalogue jargon) — analogous to the existing `experience_tier` toggle already in `profile_settings_screen.dart`.
- BASIC-tier (`experience_tier == "BASIC"`) provider configuration view: the existing `ProvidersScreen` (M22.5) gains a tier-conditional simplified path that never renders the literal words "token" or "context window" — acceptance criterion, checked by a Flutter widget test asserting those strings are absent from the BASIC-tier render tree while still present (or at least not forbidden) for ADVANCED.
- A ceiling-reached banner/flow reading `GET /usage`'s existing `limits.warning`/`limits.ceiling_reached` fields (M22.7, unchanged) and presenting them in plain language — no new backend field, pure client consumption.

## §5. Security Considerations

**5.1 — `resolved ⊆ granted ⊆ registered` must still hold with `mode` added.** The new intersection term can only ever narrow further (`allowed_ids = registry ∩ grants ∩ mode_allowed`), never widen — a user cannot gain a capability via mode that grants/registry already excluded. Tested directly: a user with a broad grant set but a narrow (`diagnostic`) mode must not see registry-and-grant-permitted capabilities the mode allowlist excludes.

**5.2 — `experience_tier` still never authorizes anything (regression, not new work).** `test_experience_tier_never_authorizes.py` is re-run completely unmodified; `mode`'s new AST/authority surface is a **separate, new, explicit** test (§7), not a relaxation of the existing one — the existing test's protected-module list and "must not appear" assertion for the string `"experience_tier"` stay exactly as they are.

**5.3 — Mode self-service is self-scoped, like `experience_tier`.** `PUT /modes` changes only the authenticated caller's own account (mirroring `POST /auth/experience-tier`'s existing pattern exactly) — no new cross-user authority; an ADMIN changing another user's mode goes through the existing M22.4 `/admin/users/{user_id}` surface, not a new mechanism invented here.

**5.4 — `mode` is never read by anything upstream of `CapabilityResolver`.** `PrincipalContext.mode` exists so the resolver can consult it, but no other module (orchestrator, approval gate, dispatcher) may branch on it directly — the single authoritative consultation point is `CapabilityResolver`, exactly matching how `ApprovalGate.execute_tool` is already the single authoritative consultation point for grants (M22.4 invariant, unchanged).

## §6. Acceptance Criteria

1. Switching `mode` never surfaces (via `CapabilityResolver.resolve()`/`is_allowed()`) a capability outside the user's own grants **or** the registry ceiling — the narrowing-only property holds under a real test with a broad grant set and a narrow mode.
2. Default `mode` (`office`, unset accounts) resolves identically to pre-M22.8 behavior (registry ∩ grants only) — zero behavior change for every existing account until a user opts into a different mode.
3. `diagnostic` mode's allowlist excludes every drafting/write/execution capability id present in the packaged registry (checked against the real `capabilities_registry.json`, not a fixture).
4. A BASIC-tier user can configure a working provider (`PUT /providers/config`, M22.5, unchanged) via the client UI without that UI ever rendering the literal strings "token" or "context window" — Flutter widget test.
5. `GET/PUT /modes` are `USER`-tier, self-scoped only (a cross-user mode-change attempt via query/body parameter, mirroring M22.7's own impersonation test pattern, is ignored/rejected).
6. `test_experience_tier_never_authorizes.py` passes completely unmodified — `mode`'s new authorization surface does not touch or relax that boundary.
7. `wc -l uri_core/core/orchestrator.py` does not increase (invariant #11) — measured exactly, not assumed, per §0.2's "net-neutral-or-negative" claim.
8. Full existing regression suite (1,433 Python tests as of the M22.7 baseline, plus new M22.8 tests) passes; Flutter suite passes including the new widget test(s) from criterion 4.
