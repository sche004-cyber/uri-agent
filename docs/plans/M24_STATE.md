### Why this is NOT VERIFIED: real regressions in the full backend regression suite

Ran `python -m unittest discover -p "test_*.py"` from scratch (the same command M23's own verification used) — **1401 tests, 6 failures**, not the 1 pre-existing, already-disclosed failure (`test_orchestrator_response_narrative...narrative_on_or_off`, the known `ProviderUnavailableError`/`unhealthy` wording mismatch on record since M23). **5 are new regressions this changeset introduced**, none disclosed by "backend targeted tests pass":

1. **`test_m20_feasibility_validation.UnavailableCapabilityIsNotPromotedTests.test_strict_single_action_proposal_for_unavailable_capability_falls_back`** — a request `"search my gmail"`, against a registry declaring only `gmail_search` (marked `unavailable_missing_dependency`), now spuriously dispatches `web_search` (`dispatcher.calls == [('web_search', ...)]`, expected `[]`). **Root cause:** `capability_planner.py`'s new `elif tool_name == "web_search":` branch scores on a `web_keywords` tuple that includes bare, generic single words — `"search"`, `"web"`, `"online"`, `"google"` — that match unrelated requests (an email search contains "search"), plus a **literal hardcoded string `"nit sikkim"`** copied verbatim from the User's own bug-report example baked directly into production scoring logic — overfitting to the one reported example rather than fixing the general keyword-matching mechanism. This is a real correctness regression: a capability the runtime has correctly marked unavailable is now silently bypassed in favor of an unrelated, available tool being dispatched instead, which URI's own `ApprovalGate`/dispatcher then actually executes against user intent that never asked for it.
2. **`test_m20_recovery_loop.CapabilityPlannerFailureReachesRecoveryTests.test_capability_planner_failure_reaches_recovery_loop`**, **`test_m20_recovery_loop.LearnedSkillFailureReachesRecoveryTests.test_learned_skill_failure_reaches_recovery_loop`**, **`test_m20_semantic_interpreter_resilience.SemanticInterpreterFailureDegradesHonestlyTests.test_capability_planner_gets_the_degraded_result_without_raising`**, **`test_m20_semantic_interpreter_resilience.SemanticInterpreterFailureDegradesHonestlyTests.test_raising_interpreter_does_not_fail_the_whole_turn`** — all four expect `result["status"] == "success"` once the recovery loop successfully recovers from an initial component failure; all four now get `"failed"`/`"unavailable"`. **Root cause:** `orchestrator.py` gained exactly two new top-level `response["status"] = ...` assignments (confirmed by `grep -n 'response\["status"\]'` — these are the *only* two places in the entire file that ever set this key), one firing whenever a single dispatched tool's `real_status` is `"failed"/"error"/"unavailable"`, the other in the "could not complete the planned workflow" branch. Both fire before/independent of the pre-existing recovery-loop machinery that these four tests exist specifically to prove still reaches an overall `"success"` outcome — the new assignment is never reset even when recovery subsequently succeeds, so any turn that hits an initial component failure now reports a terminal failure regardless of what happens next.

### A third defect, found live while launching the app for inspection, and bounded-fixed directly

Launching `flutter run -d windows` to let the User inspect the build (a fresh install, no Active Brain configured, so Phase D's new gate is the first screen reached) crashed on the very first frame: `Unhandled Exception: dependOnInheritedWidgetOfExactType<AppStateScope>() ... was called before _BrainOnboardingScreenState.initState() completed`, at `brain_onboarding_screen.dart:26` inside `initState()` (`brain_onboarding_screen.dart:20-23`). Root cause: `initState()` called `_load()`, which calls `AppStateScope.of(context)` synchronously — Flutter forbids an inherited-widget lookup before `initState()` completes; every sibling screen in this codebase already avoids this correctly (e.g. `ProvidersScreen` wraps its own initial load in `WidgetsBinding.instance.addPostFrameCallback`). Not caught by `flutter test`'s 119/119 — no test mounts `BrainOnboardingScreen`, the same missing-coverage pattern already flagged for `memory_settings.py`.

This qualified as a **bounded** fix under Claude's final-audit authority (unlike the two backend regressions above): one file, one method, a mechanical one-line-cause matching an established, already-proven convention elsewhere in the same codebase, trivially low-risk to make and re-verify alone. Fixed directly: wrapped the `initState()` call to `_load()` in `WidgetsBinding.instance.addPostFrameCallback((_) { if (mounted) _load(); })`, the same pattern `ProvidersScreen`/`MemorySettingsScreen` already use. Re-ran `flutter analyze` (0 issues) and `flutter test` (119/119) after the fix — both clean — then relaunched the app, which now reaches the first-run Brain onboarding screen without crashing.

Recommended, non-blocking, added to the remediation list for Codex: add a widget test that actually mounts `BrainOnboardingScreen` (this is exactly the class of defect a mount-only smoke test would have caught before it ever reached a running window).
