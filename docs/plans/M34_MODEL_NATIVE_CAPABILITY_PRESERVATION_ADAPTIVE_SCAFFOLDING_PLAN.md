## 1. Current-State Architecture Audit

### 1.1 C3.3 — cross-capability native multi-tool routing

The live Tier-0/Tier-1 fast path (`decision_engine_live_enabled()` defaults **True** when `URI_ENABLE_DECISION_ENGINE_LIVE` is unset — `uri_core/core/canonical_execution.py:93-102`, confirmed live-verified in `docs/plans/M33_P2_CANONICAL_LIVE_EVIDENCE_REPORT.md:39`) routes every native tool call through:

1. `native_tool_loop.run_native_tool_loop()` (`uri_core/core/native_tool_loop.py:330-429`) — builds one shared `CapabilityDirectory` per turn (M32 D1/D2), offers its full tool list to the Brain, receives `ToolCall`s back.
2. `tool_call_translator.translate_tool_calls()` (`uri_core/core/tool_call_translator.py:85-157`) — **refuses outright** if a batch's tool calls target more than one capability (`len(capabilities) > 1` at line 117), citing "R12/SR-4... explicitly BLOCKED... pending P1." This is the literal C3.3 blocker.
3. If accepted, the contract carries **one top-level `"capability"` string** for the whole batch (line 68/147-148) — the schema itself has no per-action capability field.
4. `canonical_execution._execute_multi_action()` (`uri_core/core/canonical_execution.py:186-258`) builds `steps` for `MultiActionDispatch.dispatch_chain_explicit()` by stamping **the same `capability_id`** onto every step (line 247-250: `{"capability": capability_id, "action": a["name"], ...}` for `a in actions`) — it has no way to carry a different capability per action because the contract never gave it one.
5. `decision_gates._evaluate_gates_inner()` (`uri_core/core/decision_gates.py:208-334`) reads **one** `capability_id = contract.get("capability")` (line 218) and runs the entire availability/permission/schema gate pipeline against that single id, returning a single `GateResult` with one `capability_id` field.

**Finding, evidence-based and more precise than the governance record's own framing:** `MultiActionDispatch.dispatch_chain_explicit()` (`uri_core/core/multi_action_dispatch.py:238-271`) is **already capability-heterogeneous at its own signature** — each `step` in `steps: Iterable[Mapping]` carries its own `"capability"` key (line 248), and `_action_permitted()` (line 371-415) already resolves permissions **per action's own capability**, generalized in M33 Batch B via `external_permission_resolver`/`_CAPABILITY_GRANT_ALIAS` rather than hardcoded to Gmail. Nothing in `MultiActionDispatch` itself enforces single-capability batches. The single-capability restriction is enforced **twice, above** `MultiActionDispatch`: once in `tool_call_translator.translate_tool_calls()` (an explicit refusal) and once, more fundamentally, in the **Decision Contract schema and gate pipeline** (`decision_gates.py`'s `GateResult`/`_evaluate_gates_inner` are built around exactly one `capability_id` per decision).

This means C3.3 is **not** "wire up a missing dispatch capability" — dispatch already supports it. It is: (a) stop the translator's honest refusal, (b) extend the Decision Contract schema so a `multi_action` contract can carry a capability **per action**, not one for the whole batch, and (c) extend the gate pipeline to evaluate availability/permission/risk **per distinct capability** in a batch and aggregate per-action outcomes, rather than one `GateResult` per contract. (c) is real architectural work — `GateResult` and every gate function in `decision_gates.py` currently assume one capability per decision throughout the "no capability named" branch, the "capability WAS named" branch (line 334 onward, not fully reproduced above but confirmed by direct read), and the audit/telemetry shape downstream. This is a materially larger scope item than a single-file fix, and larger than the M33 blueprint's own P1 prerequisite (permission binding), which is already fixed.

The P1 prerequisite itself (`multi_action_dispatch._action_permitted`) is confirmed fixed under M33 Batch A/P1/Batch B (commits `69d54ea`, `b86c6dd`, `85eb445`) — `_action_permitted` no longer fails open when a permission checker is merely present (§F2 finding in the M33 blueprint, repaired). C3.3's remaining blocker is genuinely M34's alone, confirmed by the same zero-match grep the governance record cites (`native_tool_loop`/`tool_call_translator`/`translate_tool_calls`/`cross-capability` do not appear in `M33_EXTERNAL_CAPABILITY_BRIDGE_BLUEPRINT.md`) — independently re-run in this session and reconfirmed.

### 1.2 Attachment-turn Brain tool-selection reliability

Original finding (`docs/plans/M32_BATCH_B_COMPLETION_REPORT.md:68`): for "what is the secret probe phrase in the file I just attached?", the Brain selected `Gmail` over the registered `read_attached_file` tool. Canonical dispatch itself behaved correctly (honest `MISSING_PARAMETER` clarification, no fabrication) — this is a model/prompt-reliability defect, not an execution-architecture one. Not independently re-tested since (disclosed in Batch C, still true — no code touching tool-selection prompting has changed since).

Root-cause candidates found by direct inspection of the live path (disclosed as **hypotheses requiring live verification**, not proven causes — see §7):

1. **No relevance scoping at all in the fast path.** `tool_schema.build_tool_schemas()` (`uri_core/core/tool_schema.py:177-227`) offers **every** dispatchable capability/action from `CapabilityDirectory.summaries()` on **every** turn, unconditionally (loop at line 215-226, no filtering). `read_attached_file` and `gmail_search`/`gmail_create_draft`/etc. all compete flatly in the same tool list with no contextual weighting.
2. **No attachment signal reaches the fast path at all.** `run_native_tool_loop()`'s signature (`native_tool_loop.py:330-338`) takes `orchestrator, session_id, user_text, principal, model_callable, max_iterations, capability_registry` — no attachment data. The legacy/canonical query-context path already computes an `attachments` list (`orchestrator.py:3518-3549`), but this is never threaded into the native tool loop's tool-schema generation or system prompt.
3. **Generic, context-free system prompt.** `_SYSTEM_PROMPT` (`native_tool_loop.py:440-444`) is four sentences with zero situational content — no mention of attachments, no disambiguation guidance between similarly-plausible tools.
4. **Lexical collision between `read_attached_file` and Gmail's own "attachment" vocabulary — confirmed, not merely hypothesized, and the opposite of what an initial draft of this document assumed.** `read_attached_file`'s actual offered description (`uri_workspace/capabilities_registry.json:145`, flowing through `CapabilityDirectory._legacy_entries()`'s `summary=feasibility_entry.get("description")` and into `tool_schema._legacy_tool_definition()` unchanged) is **not** the generic boilerplate fallback — it is a specific, well-written sentence naming attached files explicitly. The more concrete finding, found by checking Gmail's own action descriptions for comparison (`uri_core/capabilities/gmail/capability.py:31-92`): the word "attachment" appears in **four separate Gmail action descriptions** offered in the same tool list — `gmail_search` ("...attachment filters"), `gmail_read_message`/`gmail_read_thread` ("...attachment inventory"), and `gmail_read_attachment` ("Inspect an email attachment inventory or download one explicitly identified attachment..."). A flat tool list gives the Brain **four** Gmail-family entries independently reinforcing "attachment," against **one** `read_attached_file` entry — a real, concrete, lexically-grounded confusability mechanism between "email attachment" (Gmail's domain) and "attached file" (the conversation-upload domain `read_attached_file` actually serves), independent of any relevance-scoring gap. This is a stronger and more specific candidate than a generic-description theory, and argues for a targeted disambiguation fix (distinguishing "file attached to this conversation" from "email attachment" explicitly in the system prompt and/or in `read_attached_file`'s offered description) in addition to, not instead of, the relevance-scoping work in item 5 below.
5. **A relevance-scoping mechanism already exists in the codebase and is fully unwired.** `GraphifyIndex.relevant_subset()` (`uri_core/core/graphify_index.py:70-105`) is built, tested (`test_graphify_index.py:207`, `test_relevant_subset_is_small_and_filtered_not_the_whole_index`), and delegates to the same discriminating-term scorer (`capability_relevance.plausible_matches`, `uri_core/core/capability_relevance.py:92-104`) already used by the Scenario 2 connection-gate repair. It has **zero production callers** — confirmed by repository-wide search (`capability_index_hint=`, `.relevant_subset(`, `_graphify_index.` each return zero matches outside `graphify_index.py` itself and its own test file). `turn_state.py`'s `capability_index_hint` field (`turn_state.py:364,424-425,446`) is consequently always `None` in production and always reports itself `unavailable` (line 424-425).

### 1.3 Discovery/orientation landscape — full inventory

Two Explore subagents mapped this landscape independently (Graphify specifically, and all other discovery/registry mechanisms). Findings below are re-verified against source, not merely relayed.

**(A) `/graphify` CLI skill** (`.agents/skills/graphify/SKILL.md`) — a generic, project-agnostic codebase-indexing tool for a coding agent's own navigation (god nodes, community detection, wiki/HTML/JSON output). Writes to `graphify-out/`. **Not built in this repository**: `graphify-out/` contains only `.graphify_detect.json`/`.graphify_python`/`.graphify_root` — no `graph.json`, no `wiki/`, no `GRAPH_REPORT.md`. Both `SKILL.md:53` and `CLAUDE.md:6` gate their own "query first" instruction on `graph.json` existing, so per their own stated logic that fast path is currently inapplicable. **This tool has no runtime role in URI's product at all** — it is a development-time aid for the coding agent working on this repository, entirely unrelated to what the Brain sees at request time. It should not be conflated with (B)–(D) below, despite sharing a name.

**(B) `GraphStore`/`graph_engine`/`graph_ingest`** (`uri_core/core/graph_store.py`, `graph_engine.py`, `graph_ingest.py`, `graph_context.py`) — M23's per-user knowledge graph (entities/relationships), live-wired into both the orchestrator (`orchestrator.py:52-53,344,3536-3551` — `graph_self_context` injected into every query-context build, degrading to `None` on failure) and the server (`server.py:114-127`, six read-only `USER`-scoped REST routes at `server.py:2213-2325`). Per-user file isolation is proven (`test_graph_isolation.py`). **Mechanically enforced advisory-only boundary**: `test_graph_authority_boundary.py:57-90` AST-scans real import statements and asserts none of `dispatcher.py`/`approval_gate.py`/`approval_store.py`/`capability_registry.py`/`capability_resolver.py` ever import any `graph_*` module, and none of the `graph_*` modules ever import `model_providers`/`model_router`/`dispatcher`/`approval_gate`/`approval_store`. This is a genuinely different data model (per-user entities/edges, ingested from confirmed memory) from (C) below, despite living in the same "graph" family.

**(C) `graphify_index.py`** (`uri_core/core/graphify_index.py`) — "Graphify Foundation," a **system-level, install-wide, non-authoritative pointer index** over `CapabilityDirectory` (capabilities), `SkillMemory` (skills), `WorkflowPlanner` (one procedure template), and `MemoryStore` (memory pointers only — see gap noted in §2). Every record stores a pointer back to its real authority, never a copy of content (`graphify_index.py:1-33`docstring; enforced by `test_graphify_index_authority_boundary` tests mirroring (B)'s own AST proof). Degrades safely on any collaborator failure or corrupted persisted file (quarantine-not-delete, `load_index()` line 304-323). Built once at server startup (`server.py:726-779`, `_GraphifyIndexLoader`) into a module-level global `_graphify_index`. **Confirmed by direct grep: this global has zero downstream readers anywhere in `uri_core/` beyond the loader that builds it** — it is loaded and then never consulted by any live request-path code. Structurally, this module is already a close match for the "Obsidian-style lightweight metadata/index" pattern the task description raises as a candidate implementation model: small frontmatter-like records (`id`/`kind`/`summary`/`dependencies`/`availability`/`pointer`) pointing back into authoritative stores, plain JSON persistence, no external dependency, incremental per-scope refresh (`refresh()`, line 273-301) already implemented.

**(D) `CapabilityDirectory`** (`uri_core/core/capability_directory.py:390-502`) — the actual live discovery mechanism the Brain's tool list is built from. Explicitly an adapter (docstring line 1-25): "stores nothing, executes nothing, grants nothing." Projects `CapabilityFeasibility` (legacy JSON registry) + `MultiActionCapabilityRegistry` (Gmail-family) + one static workflow-procedure entry into a two-level view (`summaries()` = Level 1, cheap, no live checks; `describe(id)` = Level 2, one live availability check, loaded only once a capability is selected). Built fresh per call site; as of M32 D1/D2 (`build_turn_state_and_directory`, `decision_engine.py:941-978`), exactly **one** instance is built and shared for the whole turn (both the gate pipeline and `build_tool_schemas()` reuse it — `native_tool_loop.py:353-368`), eliminating a real, measured double-OAuth-refresh cost. Already carries `aliases`/`intent_signals`/`category`/`foundational` metadata fields per capability (M33 Batch B) — i.e. it already carries most of the metadata an Obsidian-style index would want, just not exposed as a persisted file.

**(E) `CapabilityDiscoveryEngine`** (`uri_core/capabilities/discovery.py:25-`) — a **separate** lexical-overlap relevance ranker, scoped only to the Gmail-family multi-action registry, wired live into `MultiActionDispatch.model_context()` (`multi_action_dispatch.py:66,121`) for the `"relevant_capabilities"` field shown to the model during progressive Gmail-action discovery. This is a third, independently-implemented near-duplicate of the same "score capability relevance against user text" problem that `CapabilityDirectory._find_overlaps()`/`_word_tokens()` (capability-overlap detection) and `capability_relevance.plausible_matches()` (the "tightened," discriminating-term version used by the Scenario 2 gate repair and by `graphify_index.relevant_subset()`) also each separately solve.

**(F) `skill_router_v1.py`/`skill_evaluator_v1.py`/`build_skill_registry_v1.py`** (repo root) — a fully **dead, standalone** pipeline. `orchestrator.py:197-224` documents its own explicit removal: the shadow pipeline "is no longer run on any live turn," `SkillEvaluatorV1.evaluate_from_context_budget()` never applied its own relevance floor (silently reported no capability gap on effectively every request — `SKILL_ROUTER_V1_ARCHITECTURE_AUDIT.md`), and it read a stale, machine-specific `uri_workspace/skill_registry.json` snapshot with mostly-empty descriptive fields. `enable_skill_router_shadow` remains an inert constructor flag nothing reads. Confirmed zero references under `uri_core/` by the audit doc itself and independently reconfirmed this session.

**(G) Memory/history — four genuinely separate stores, no unifying index (deliberately, per each module's own docstring):** `MemoryStore` (`user_memory.py`, consent-gated durable facts), `ExperienceStore` (`experience_store.py`, Brain-approved interaction summaries), `FactManager` (`fact_manager.py`, session-scoped task facts), `ConversationHistoryStore` (`conversation_history.py`, raw transcript, explicitly "never authority" per its own docstring), plus a family of evidence stores (`evidence_context.py`, `evidence_fact_integrity.py`, `evidence_search.py`, `uri_core/services/evidence_*`). `orchestrator.py` queries each independently; `context_builder.build_task_context()` merges facts+evidence for one task only, not a cross-store index. `graphify_index.py`'s `_index_memory_pointers()` covers only `MemoryStore`, not the other three — a genuine, disclosed current-state gap, not an oversight to silently work around.

**(H) `CapabilityResolver`/`CapabilityGrantsStore`** (`uri_core/core/capability_resolver.py`) — an authorization-side lookup ("what is this principal granted"), distinct in kind from every "what exists" mechanism above; not itself a duplicate, but worth naming so it is not mistaken for one during M34 implementation.

## 2. Overlap/Duplication Map

| Concern | Mechanisms involved | Verdict |
|---|---|---|
| "What capabilities/tools exist, with what metadata" | (D) `CapabilityDirectory` (live, authoritative-adapter) vs. (C) `graphify_index` (live-built, dead-read, redundant projection of the same data plus skills/workflows/memory) | **Redundant.** (C) re-derives exactly what (D) already exposes (`graphify_index._index_capabilities()` literally calls `capability_directory.summaries()`/`.describe()`), then goes unread. Not a data-integrity risk (pointers only, degrades safely) but a wasted-build / dead-weight risk and a "two discovery layers" naming/maintenance hazard exactly matching the task's "do not create Graphify plus another equivalent runtime map under a different name" concern — except here it is the *same* name, doing the *same* kind of job, in two disconnected places. |
| "How relevant is capability X to this user text" | (E) `CapabilityDiscoveryEngine` (Gmail-only) vs. `CapabilityDirectory._find_overlaps`/`_word_tokens` (overlap detection, not relevance) vs. `capability_relevance.plausible_matches` (discriminating-term, used by Scenario 2 gate + dead `graphify_index.relevant_subset`) | **Three independent lexical-scoring implementations** for closely related but not identical purposes (Gmail-action suggestion; legacy/multi-action identity-overlap detection; general capability-plausibility for gate/index use). None calls another. A genuine consolidation opportunity, not merely cosmetic — three code paths to keep correct in step. |
| "What skills exist and how good is URI at them" | (F) `skill_router_v1`/`skill_evaluator_v1`/`build_skill_registry_v1` (dead) vs. `graphify_index._index_skills()` reading `SkillMemory.list_skills()` (live-built, dead-read) | **Two unrelated, both non-functional-in-practice mechanisms** for "skill" discovery — one abandoned by explicit prior decision, one built but unwired. Neither currently informs a live decision. |
| "Codebase/dev-navigation graph" vs. "runtime knowledge graph" vs. "runtime discovery index" | (A) CLI Graphify, (B) `GraphStore` per-user entity graph, (C) `graphify_index` system index | **Naming collision only, not functional overlap** between (A) and (B)/(C) — (A) never runs against URI's own runtime data and has no code-level relationship to (B)/(C) at all. (B) and (C) are functionally distinct (per-user facts-as-entities vs. install-wide capability/skill/workflow/memory pointers) and both correctly avoid each other by design (`graphify_index.py:5-10` says so explicitly), so this pairing is **not** duplication — it is two legitimately different indexes that happen to both be called "graph"/"graphify," which is a naming-hygiene problem, not an architecture problem. |
| Memory/history discovery | (G) four separate stores, partially pointed-to by (C) | **Not redundant** — each store's separateness is an intentional, documented design decision (e.g. conversation history is explicitly "never authority"). The gap is coverage (three of four stores have no index pointer at all), not duplication. |

**Summary verdict on the task's core question:** URI does **not** currently have "Graphify plus another equivalent runtime map under a different name" in the sense of two competing *authoritative* stores. It has something narrower but still real: **one live, correct, but narrow discovery adapter (`CapabilityDirectory`, capabilities only) plus one broader, correctly-designed, but completely disconnected discovery index (`graphify_index`, capabilities+skills+workflows+memory) that duplicates (D)'s capability data and then goes nowhere.** The fix is not to build a new layer; it is to connect the one that already exists correctly and retire or intentionally scope the dead skill-registry trio.

## 3. Likely Latency Consequences

Evidence-grounded, not measured live this session (flagged for §7 live verification):

1. **Full unfiltered tool-schema dump every native-tool-loop turn.** `build_tool_schemas()` iterates every `CapabilityDirectory` summary and, for `multi_action` entries, every action's schema (`tool_schema.py:214-226`) — no caching beyond the one-shared-`CapabilityDirectory`-per-turn scope M32 D2 already achieved. As capability count grows (M33/M33.1 external capabilities are additive to this same registry), the per-turn prompt token cost of the tool list grows linearly and unconditionally, regardless of what the turn actually needs — this is the concrete mechanism behind the task's "avoid loading/scanning every capability... unnecessarily" concern, and it is currently unaddressed.
2. **`graphify_index` startup build cost is paid for zero runtime benefit today.** `_GraphifyIndexLoader` (`server.py:726-779`) builds/loads the index at startup unconditionally; since nothing reads it afterward, this is pure sunk cost with no offsetting latency win — not large, but real, and worth resolving by wiring it up rather than leaving it as dead startup work.
3. **Three independent lexical-relevance passes could each run per turn if all were wired** (they currently are not all wired together) — a naive M34 implementation that adds a fourth without consolidating the existing three would compound this rather than fix it.
4. **`CapabilityDirectory.describe()`'s Level 2 live availability check** (`capability_directory.py:446-495`) is already correctly scoped to exactly one capability, on demand — this part of the existing design already matches the "cache/scope per-turn, don't scan everything" principle and should be preserved as the model for any new scoping work, not replaced.
5. **Per-turn `CapabilityDirectory` sharing (M32 D2) is the right precedent to extend, not duplicate.** Any M34 discovery-layer work should reuse the same turn-scoped object/cache-key discipline already proven out for `CapabilityDirectory`, rather than introducing a second per-turn caching convention.

## 4. Proposed M34 Architecture

### 4.1 Answering the task's A/B/C question

**Evaluated:**
- **(A) Graphify becomes the canonical discovery layer** — rejected. "Graphify" is not one thing in this codebase; making an ambiguous name canonical would deepen the exact naming-collision problem identified in §2, and the CLI tool (A) has no runtime relationship to URI at all.
- **(B) Graphify sits behind a lighter URI Discovery Index** — **this is effectively already built and merely disconnected.** `graphify_index.py` already **is** a lightweight, pointer-only, Obsidian-metadata-style discovery index sitting in front of `CapabilityDirectory`/`SkillMemory`/`WorkflowPlanner`/`MemoryStore`. The correct M34 direction is not to build a new "URI Discovery Index" but to **finish wiring the one that already exists** into the two places that currently bypass it (`native_tool_loop.py`'s tool-schema generation, and `turn_state.py`'s `capability_index_hint`), and to extend its coverage (ExperienceStore/ConversationHistory/evidence stores) only if a live need is demonstrated, not speculatively.
- **(C) Merge useful functionality into another existing mechanism** — partially the right move for the *skill-registry trio* (F): rather than reviving `skill_router_v1`/`skill_evaluator_v1` as a fourth discovery path, their one genuinely reusable idea (scored, floor-gated skill suitability) should be evaluated against whether `graphify_index`'s existing `_index_skills()`/`relevant_subset()` already covers the need once wired up — likely yes, since both ultimately read `SkillMemory`.

**Decision: (B), realized as "wire up and consolidate the existing `graphify_index` + `capability_relevance` machinery," not "build something new."** This is the only option consistent with the task's explicit principle ("do not create Graphify plus another equivalent runtime map under a different name") given that the equivalent map already exists under exactly that name.

### 4.2 Desired runtime behavior, mapped to concrete mechanisms

| Desired behavior | Mechanism (already exists) | M34 work required |
|---|---|---|
| Brain knows a discovery/orientation mechanism exists | `_SYSTEM_PROMPT` (`native_tool_loop.py:440`) | Extend the prompt to state that the offered tool list is already relevance-scoped, and (for the attachment case) that attachments are a strong routing signal — see 4.3. |
| Tool/memory lookup can use it to locate the right authoritative source | `graphify_index.relevant_subset()` → `capability_relevance.plausible_matches()` → `CapabilityDirectory` | Call `relevant_subset()` (or the equivalent live-directory scorer, see 4.3 design note) from `build_tool_schemas()`, gated by turn context, before the tool list is sent to the Brain. |
| Avoid loading/scanning every capability unnecessarily | N/A today (full scan every turn) | New: bound the offered tool list by relevance score + always-include `foundational` capabilities (the directory already flags these — `capability_directory.py:143-170`) + always-include any capability the current turn's attachment/context signal points to. |
| Cache per-turn resolution where appropriate | M32 D2's shared `CapabilityDirectory` | Extend the same turn-scoped object to also carry the resolved relevant-subset result, computed once, not duplicated across `build_tool_schemas()` and any gate-side lookup. |
| Graphify maps skills/memory/history/capabilities by default unless a demonstrably better native locator exists | `graphify_index.py` already does capabilities/skills/workflows/memory (partial) | No new locator needed — extend `_index_memory_pointers()` coverage only if a demonstrated turn-level need for `ExperienceStore`/`ConversationHistory`/evidence-store discovery emerges from M34's own live testing; do not build ahead of demonstrated need. |
| Authoritative stores remain authoritative | Already true — `graphify_index`/`CapabilityDirectory` are both pointer/adapter-only by construction, AST-enforced | Preserve as an invariant; any M34 change must keep passing the existing authority-boundary tests unmodified in spirit. |
| Do not create Graphify plus another equivalent runtime map under a different name | — | Explicitly the governing constraint on 4.1's decision. |

### 4.3 C3.3 design direction (not a final design — flagged for implementation-phase detailing)

1. Extend the `multi_action` Decision Contract shape so each entry in `actions` may carry its own `capability` (falling back to the contract-level `capability` for backward compatibility with every existing single-capability caller/test).
2. Relax `tool_call_translator.translate_tool_calls()`'s refusal: build a per-action `(capability, action, inputs)` list instead of asserting one shared capability; keep the existing "unknown tool → per-call error, never a dispatch" behavior unchanged.
3. Extend `decision_gates.py` to evaluate the gate pipeline **once per distinct capability** referenced in a batch, aggregate to a per-action outcome list (not a single `GateResult`), and only allow dispatch for actions whose own gate passed — a heterogeneous batch must be able to partially succeed/partially deny, each outcome individually honest, mirroring the existing "never a partial or silent dispatch" principle already stated in `tool_call_translator.py`'s docstring.
4. `canonical_execution._execute_multi_action()` and `MultiActionDispatch.dispatch_chain_explicit()` need **no signature change** — they already accept per-step capabilities; only the contract that feeds them needs to stop collapsing to one id.
5. This is squarely a live-model-selection-behavior change (does the Brain actually propose valid cross-capability batches, and does it do so safely) — flagged for mandatory live/local-model verification, not something a unit-test suite alone can close out (see §7).

### 4.4 Attachment-turn reliability design direction

1. Thread an `attachments_present: bool` (and ideally a short attachment-type/name hint) from the orchestrator's existing attachment computation (`orchestrator.py:3518-3549`) into `run_native_tool_loop()`'s signature and through to `build_tool_schemas()`.
2. When true, bias `read_attached_file` into the offered tool list's front position — its own description (`capabilities_registry.json:145`) is already specific and does not itself need rewriting (§1.2 item 4, corrected). The higher-value fix is disambiguating it **from Gmail's own "attachment" vocabulary**, not making it more distinctive in isolation: either (a) append one clarifying clause to `read_attached_file`'s offered description distinguishing "a file attached to this conversation" from "an email attachment" explicitly, and/or (b) add the same distinction to the system prompt (item 3). 3. Extend `_SYSTEM_PROMPT` with one concrete sentence naming attachment-turn behavior explicitly: state that a file is attached to *this conversation* (distinct from any email attachment Gmail tools might reference) and that `read_attached_file` is the tool for it. This directly targets the confirmed four-vs-one lexical imbalance found in §1.2 item 4, and should be tried and live-verified before the more structural relevance-scoping work in 4.2, since it may resolve the disclosed defect on its own.
4. Do **not** claim this resolved until re-tested against the exact Batch B scenario ("what is the secret probe phrase in the file I just attached?") on the same or equivalent local model, per the Evidence Integrity Rules — a code change without a fresh live re-run is not sufficient evidence.
