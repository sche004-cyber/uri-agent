## §0. Clarifications

One factual discrepancy was found during pre-audit between the architecture doc and the actual repository state, and one implicit assumption needs to be made explicit before Gemma implements.

**0.1 — `cryptography` is NOT currently an installed dependency. RESOLVED — User accepted Option 1.**
URI_M22_ARCHITECTURE.md §6.4 states: *"cryptography is already an installed transitive dependency — no new dependency."* This is false in the current repo: `pip show cryptography` reports "Package(s) not found", it does not appear in `requirements.txt` (which lists only `pypdf`, `python-docx`, `fastapi`, `uvicorn`, `python-multipart`, `requests`, `openpyxl`, `python-pptx` — none of which pull in `cryptography` transitively), and no `.venv` install of it exists. Encrypted-at-rest key storage cannot be built on a library that isn't there.

**User decision (accepted at ACCEPTED gate):** add `cryptography>=42` as a new, explicit line in `requirements.txt` and use its `Fernet` symmetric-encryption recipe (AES-128-CBC + HMAC, authenticated) for `provider_keys.py`, with a fixed key derived once (PBKDF2-HMAC-SHA256, matching the KDF `user_accounts.py` already uses for password hashing) from a secret sourced only from the environment (`URI_PROVIDER_KEY_SECRET`), never hardcoded, never persisted in plaintext alongside the ciphertext it protects. This is now binding scope for Gemma's implementation, not an open question.

**0.2 — Per-user storage location.**
§6.4 says key/provider-config storage is "deleted with the user's directory." The repo does have exactly this concept already: `portable_paths.user_scoped_path(user_id, filename)` resolves to `uri_workspace/users/<user_id>/<filename>` (see `user_accounts.py`'s own docstring, which documents profile/memory/growth/sessions/approvals all living there). This plan uses that existing helper for `providers.json` and `provider_keys.enc` rather than inventing a new per-user directory convention — no clarification needed here, noted only so Gemma implements against the real helper instead of a new one.

If no objection is raised, both are treated as **ACCEPTED-by-default** in this plan's design below; the User can strike this note and just modify §0 directly if a different resolution is wanted.

## §1. Objective

Per URI_M22_ARCHITECTURE.md §22.1 (M22.5): introduce `ProviderDescriptor`/`ModelDescriptor` with confidence labelling, a packaged static provider catalogue, one OpenAI-compatible HTTP adapter (covering OpenRouter/Groq/LM Studio/llama.cpp/OpenAI's shared `/chat/completions` wire shape), per-user provider configuration, and encrypted write-only per-user API-key storage — then complete the shadow-provider migration begun in M22.1 by porting the credential-hygiene behavioural guarantee (`test_credential_hygiene.py`) onto the real key store and deleting `hermes_service.py` / `uri_core/core/semantic_interpreter.py` and their two now-redundant tests.

This is the milestone that lets a user configure a second, real model backend besides local Ollama — using their own key, never URI's.

## §3. Scope — file by file

**NEW `uri_core/core/model_providers/openai_compatible_provider.py`**
- `OpenAICompatibleProvider(ModelProvider)` — implements `complete()` against any `/chat/completions`-shaped HTTP endpoint (`base_url` + bearer-token auth), and `describe()` as a cheap, timeout-bounded, exception-safe reachability probe (mirrors `OllamaProvider.describe()`'s discipline — never raises, `available=False` + `detail` on failure).
- Raises the existing `ProviderError` subclasses (`ProviderUnavailableError`, `ProviderTimeoutError`, `ModelNotFoundError`, `ProviderResponseError`) from `model_providers/base.py` — no new exception hierarchy.
- **New, and load-bearing:** a distinct exception (or a `ProviderResponseError` subclass), e.g. `ProviderAuthenticationError`, raised specifically on HTTP 401/403 from the backend. This is what lets `build_provider`/callers implement "auth failure stops, never silently falls back" (§5.3) — that logic does not belong in `ModelRouter` (M22.6, out of scope here), but the *signal* it will need has to exist now, distinguishable from a generic `ProviderUnavailableError`.

**NEW `uri_core/core/provider_registry.py`**
- `ProviderDescriptor` (dataclass): `provider_id`, `display_name`, `adapter` (`"ollama" | "openai_compatible"`), `base_url` (default per provider, user-overridable), `models: List[ModelDescriptor]`.
- `ModelDescriptor` (dataclass): `model_id`, `context_tokens: ConfidenceValue`, `pricing: Optional[ConfidenceValue]` — every numeric field wrapped so its confidence (`KNOWN | ESTIMATED | UNAVAILABLE`) travels with the value and can never be read as a bare, un-labelled number (§6.3 of the architecture doc). A minimal `ConfidenceValue` dataclass (`value: Optional[float|int]`, `confidence: str`) is defined here since nothing else in the codebase has it yet.
- A packaged static catalogue (`PROVIDER_CATALOGUE: List[ProviderDescriptor]`) covering Ollama (unchanged) + a small, honest set of OpenAI-compatible entries (OpenRouter, Groq, LM Studio, OpenAI itself) with only what is actually provider-documented marked `KNOWN`; everything else `UNAVAILABLE` — no invented numbers.
- Per-user provider *configuration* (which catalogue provider(s) a user has enabled, their own `base_url` override if any) persisted at `user_scoped_path(user_id, "providers.json")` — never key material, which lives only in `provider_keys.py`'s own store.

**NEW `uri_core/core/provider_keys.py`**
- `ProviderKeyStore` — per-user, encrypted-at-rest (`cryptography.fernet.Fernet`, per §0.1), keyed by `(user_id, provider_id)`, persisted at `user_scoped_path(user_id, "provider_keys.enc")`.
- `set_key(user_id, provider_id, raw_key: str) -> None` — the only write path. Encrypts and overwrites; never appends plaintext anywhere, never logs `raw_key`.
- `has_key(user_id, provider_id) -> bool` and `describe_key(user_id, provider_id) -> Optional[dict]` (returns only a stored last-4 suffix + "configured" boolean — never the key, never enough of it to reconstruct or brute-force meaningfully).
- `get_key_for_use(user_id, provider_id) -> Optional[str]` — the **only** function that ever decrypts and returns the real key, and it exists *only* to be called from provider-construction code at the moment of use (never cached beyond that call, never returned across a process/API boundary). This function itself must not be reachable from `provider_semantic_interpreter.py`/`model_reasoning_adapter.py`/`response_drafting.py`/`document_composer.py` directly — see invariant #4 in §5.4; those modules call `build_provider(role, principal)`, which is the one place permitted to call it.
- **No delete-on-read, no read-back endpoint anywhere** (§5.2).

**MODIFY `uri_core/config/model_roles.py`**
- `build_provider(role: str, principal: Optional[PrincipalContext] = None, roles_path=...) -> ModelProvider` — extended signature per §7.3 of the architecture doc. When `principal` is `None` or the resolved provider is `"ollama"`, behavior is byte-for-byte unchanged from M21 (zero-behavior-change for every existing caller/test that doesn't pass a principal). When a role resolves to `"openai_compatible"` for a given principal, `build_provider` looks up that user's configured `base_url`/`model` from `provider_registry.py` and calls `provider_keys.get_key_for_use(principal.user_id, provider_id)` to construct the `OpenAICompatibleProvider` — this is the only new call site for key retrieval in the whole codebase.
- `UnknownModelProviderError` behavior is preserved unchanged (§5.5) — an unregistered `provider` string still raises immediately, never falls back to Ollama silently.
- Add two roles per §6.5 of the architecture doc: `diagnostics`, `background` (both default `"ollama"`, light tier) — **not** `implementation`, which has no consumer yet and is explicitly out of scope.

**MODIFY `uri_core/app/server.py`**
- `POST /providers/keys` — body `{provider_id, api_key}`. USER-classified (own key only; a caller can never set another user's key — `user_id` comes only from `_resolve_authenticated_user_id`/`_resolve_principal`, never from the request body). Returns `{provider_id, configured: true, last_four}` — never the key.
- `GET /providers` — the merged view of the static catalogue + this user's per-provider configured/not-configured status (`has_key()` only, never `describe_key`'s raw material beyond last-4) + a cheap `describe()` reachability probe per configured provider. USER-classified.
- `PUT /providers/config` — sets a user's chosen `base_url`/model override for a provider they've already keyed. USER-classified.
- **Deliberately not built:** any `GET /providers/keys` or equivalent read-back route (§5.2, and the architecture doc's explicit "there is no GET").

**MODIFY `uri_core/app/route_classification.py`**
- Add the three new `(method, path)` pairs above as `USER`, bump `EXPECTED_ROUTE_COUNT` from 47 to 50, matching `test_m22_3_route_authorization.py`'s enumeration-and-count discipline exactly as M22.4 did for its 3 admin routes.

## §5. Security Considerations

**5.1 — Write-only, always.** `provider_keys.py` exposes no function, and `server.py` wires no route, that returns a raw key once stored. `describe_key()`/`GET /providers` may only ever return a boolean and a last-4 suffix.

**5.2 — Encrypted at rest.** The plaintext key string is never written to disk. `Fernet` (authenticated symmetric encryption) is used with a key derived from an environment-sourced secret (`URI_PROVIDER_KEY_SECRET`), never hardcoded and never itself stored beside the ciphertext it protects — mirrors the "never hardcoded, never silently substituted" discipline `test_credential_hygiene.py` already enforces for `GROQ_API_KEY`/`GEMINI_API_KEY`.

**5.3 — No silent fallback on auth failure.** `OpenAICompatibleProvider` raises a distinguishable authentication error (not `ProviderUnavailableError`) on HTTP 401/403. `build_provider`'s own extended path does not catch and retry this against a different provider — it propagates. (Full fallback-chain *selection* logic is M22.6/`ModelRouter`, explicitly out of scope here — this milestone's job is only to make sure the *signal* exists and is not swallowed.)

**5.4 — Invariant #4 (architecture doc §19.4).** `provider_keys` is never imported by `provider_semantic_interpreter.py`, `model_reasoning_adapter.py`, `response_drafting.py`, or `document_composer.py` — enforced by a new AST-scan test (`test_provider_keys_boundary.py`), the same technique `test_experience_tier_never_authorizes.py` already uses for the structurally identical `experience_tier` guarantee. Only `config/model_roles.py`'s `build_provider` may import `provider_keys`.

**5.5 — No key ever appears in a log, audit record, prompt, or response.** `ApprovalGate`'s `_record_audit_safely` calls and any new server-side logging around `/providers/*` must pass only `provider_id`/`configured`/`last_four` — never the payload's `api_key` field. This is verified by the endpoint test asserting `AuditTrail` records for these routes never contain the raw key substring used in the test.

**5.6 — `UnknownModelProviderError` unchanged.** Configuring a role for a provider string this codebase doesn't implement still raises immediately at construction time — the M21 "never silently substitute" discipline is preserved, not weakened by adding a second real adapter.

## §6. Acceptance Criteria

1. A user can `POST /providers/keys` with their own OpenAI-compatible provider key, then have a role that targets that provider (via `uri_workspace/model_roles.json` or the new per-user `providers.json` config) actually answer a real turn using it.
2. No route, log line, audit record, or model prompt/response ever contains a raw API key value, verified by test.
3. `GET /providers` returns catalogue + per-user configured status + last-4 suffix only; there is no route anywhere that returns a full key.
4. An invalid/revoked key produces an explicit authentication error surfaced to the caller — never a silent fallback to a different provider or a different key.
5. `UnknownModelProviderError` is still raised for an unregistered `provider` string, unchanged from M21.
6. `test_provider_keys_boundary.py` (invariant #4) passes: none of the four prompt-assembly modules import `provider_keys`.
7. `hermes_service.py`, `uri_core/core/semantic_interpreter.py`, `test_semantic_interpreter.py`, and `test_credential_hygiene.py` are deleted, and `test_provider_keys_hygiene.py` proves the same behavioural guarantee (env/store-only credential sourcing, never hardcoded, never silently substituted) against the real `ProviderKeyStore`.
8. `route_classification.py`'s `EXPECTED_ROUTE_COUNT` is updated (47 → 50) and `test_m22_3_route_authorization.py`'s enumeration test still passes with the three new routes correctly classified USER.
9. `wc -l uri_core/core/orchestrator.py` is unchanged (still 5,461 lines) before and after this milestone.
10. Full existing regression suite (1,241 Python tests as of the M22.4 baseline, plus the new M22.5 tests) passes; Flutter suite (106 tests) is unaffected since §8 declares `UI IMPACT: NONE`.

## §8. UI Impact

**UI IMPACT: REQUIRED.**

Justification: this milestone adds the one genuinely new sensitive user-facing action in M22 — supplying a personal API key — and a settings surface to see which providers are configured (without ever seeing the key back). `uri_ui` already has a `settings_shell.dart` and (per the working tree) an `admin_grants_screen.dart` precedent from M22.4 for a similarly-shaped per-user configuration screen. This milestone's UI work is a `providers_screen.dart` (or an addition to `settings_shell.dart`) that:
- lets the user select a provider from the catalogue and paste in a key (a masked/password-style input, submitted once, never redisplayed — the client must not cache the raw value after submit),
- shows configured/not-configured + last-4 per provider,
- shows an explicit error state on an authentication failure (never a silent "it just uses Ollama now").

Per the AO-4 cycle rule, this UI work is part of the same M22.5 milestone (not deferred), and Antigravity's audit for this milestone must include UI/backend parity verification (the client hits exactly the three real endpoints in §3, no additional client-invented ones) before this milestone can reach `VERIFYING`.
