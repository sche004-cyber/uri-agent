## CLAUDE VERIFICATION REPORT

**Verdict: STATE: NOT VERIFIED.**

Independent inspection was performed directly against the working tree (`git diff HEAD`), the real production wiring (`uri_core/app/server.py`), and by running the tests myself (not taken on Gemma's or Antigravity's report). However, a real, reproducible defect was found that violates the accepted plan's own explicit written requirement and was not caught by any of the 45 new tests or the audit.

### Finding 1 (blocking) — `principal` is never threaded to the reasoning or document-composition leaf modules in production, so per-user `openai_compatible` provider configuration silently breaks those two roles

The accepted plan (§3, "MODIFY the four leaf modules' own callers") explicitly requires:

> "M22.6 adds passing that same already-resolved `principal` into `self.semantic_interpreter.interpret(...)` and `self.model_reasoning_gateway`'s callable, and `document_composer.compose(...)`'s call site."

This was done for `semantic_interpreter` (via `UriOrchestrator.__init__`: `ProviderSemanticInterpreter(principal=principal)`, `uri_core/core/orchestrator.py:136`) and for `draft_response()` (per-call `principal=self.principal` at `orchestrator.py:3229`, and `response_drafting.py` correctly accepts `principal` as a fresh per-call keyword argument).

It was **not** done for the other two:

1. **`OllamaReasoningAdapter` (the reasoning/"Brain" role — the single most heavily used role in the system).** `uri_core/core/model_reasoning_adapter.py`'s `__call__()` now correctly calls `get_router().attempt(ROLE_REASONING, self._principal, ...)`, but `self._principal` can only come from `__init__`, and there is no per-call path to it (`ModelReasoningGateway.reason()` has no `principal` parameter — confirmed by reading `uri_core/core/model_reasoning_gateway.py`, and `orchestrator.py`'s call site at line 744 passes no `principal`). The only place that constructs `OllamaReasoningAdapter` is `uri_core/app/server.py`, at two sites — both construct it with **no principal at all**:
   - Line 135 (module-level legacy `_orchestrator`) — `principal=None` here is arguably correct (no authenticated identity exists at that scope).
   - **Line 349, inside `_build_user_context(user_id)`** — `OllamaReasoningAdapter()` is constructed with zero arguments even though the real `principal` for that exact user (`PrincipalContext(user_id=user_id, role=role, device_id=None)`, built two lines earlier at line 291) is already sitting in scope and is already passed to `UriOrchestrator(..., principal=principal)` on line 358, one line below. `server.py` is not in this milestone's diff — it was never touched.

2. **`DocumentComposer.compose()`.** All three real (non-test) construction sites — `uri_core/services/institutional_drafting.py:179`, `uri_core/tools/generate_document.py:132`, `uri_core/tools/gmail_create_draft.py:104` — call `DocumentComposer()` with no arguments. None of these three files were touched by this milestone and none currently carry a `principal` in scope at all (confirmed: zero occurrences of "principal" in any of the three files), so `self._principal` is always `None` in every real document-composition call.

**Why this is a real defect, not a cosmetic gap:** `uri_core/config/model_roles.py:build_provider()` raises `UnknownModelProviderError` when a role is configured for `"openai_compatible"` and `principal is None` (lines 191-197: *"no principal was supplied - cannot look up per-user provider config or key"*). `ModelRouter.attempt()` (`uri_core/core/model_router.py:242-258`) only catches `ProviderAuthenticationError` (re-raised immediately) and the three transient errors (`ProviderUnavailableError`/`ProviderTimeoutError`/`ModelNotFoundError`, which advance the fallback chain) — `UnknownModelProviderError` is not in either list, so it propagates straight out of `attempt()`. For the reasoning role this is caught by `orchestrator.py`'s broad `except Exception` at line 769 and turned into `{"status": "reasoning_failed", ...}` — i.e., **every single reasoning/planning call silently and permanently fails** for any user who configures a non-Ollama (`openai_compatible`) provider for `ROLE_REASONING` via the M22.5 provider-configuration feature, even though that per-user configuration is exactly what M22.5 shipped and exactly what this milestone's router exists to consult. The same failure mode applies to `ROLE_DOCUMENT_COMPOSITION` (caught there by `DocumentComposer.compose()`'s own `except ProviderError` — but `UnknownModelProviderError` is a `ValueError` subclass, not a `ProviderError` subclass, so it is **not** caught there either; it propagates out of `compose()` uncaught to that call's own caller).

This is not covered by any of the 45 new tests: `test_model_router_freshness.py`'s `TestOllamaReasoningAdapterFreshness`/`TestDocumentComposerFreshness` construct these classes directly with an explicit `principal=` kwarg in the test, which exercises the router mechanics correctly in isolation but never exercises the real `server.py` wiring that is actually broken. `test_model_router_budget_seam.py`'s `TestUnknownModelProviderError` tests a different scenario entirely (an unregistered provider **name**, e.g. `"nonexistent_provider_xyz"` passed via `provider_id_override`) — not the "role configured for `openai_compatible`, principal missing" path. Acceptance criterion 7 ("resolve a fresh `ModelRouter.attempt()` call per real invocation") is technically satisfied by all three modules mechanically calling the router per call — but the router is being fed a permanently-`None` principal in production for two of the three roles that matter, which defeats the actual purpose of threading principal through at all. This is exactly the class of "mechanically passing test, functionally broken in production" gap this verification pass exists to catch.
