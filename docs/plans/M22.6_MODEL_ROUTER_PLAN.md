## §0. Clarifications

Two things the architecture doc states at a level that needs to be made concrete before Gemma can implement them correctly. Neither changes the milestone's objective; both are precision the accepted plan needs to carry so Gemma doesn't have to improvise a design decision.

**0.1 — Three of the four M21 leaf modules cache their provider at construction time, not per call.** Verified by reading all four current call sites:
- `provider_semantic_interpreter.py`: `ProviderSemanticInterpreter.__init__` sets `self.provider = provider or build_provider(...)` — resolved once, reused forever.
- `model_reasoning_adapter.py`: `OllamaReasoningAdapter.__init__` does the same.
- `document_composer.py`: `DocumentComposer._get_provider()` lazily resolves once, then caches in `self._provider`.
- `response_drafting.py`: `draft_response()` is a **plain function** — `provider = provider or build_provider(ROLE_DRAFTING)` runs fresh inside the function body on every call. This one is already correct for per-call resolution.

This matters because `server.py`'s `_user_contexts` dict (confirmed: `# and cached for the process lifetime in _user_contexts below`) caches each user's `_UserContext` — and therefore their `UriOrchestrator`, and therefore its `semantic_interpreter`/reasoning adapter — for the life of the process, not per-request. If the first three modules keep resolving their provider once at construction, `ModelRouter`'s health checks, cooldowns, and fallback would only ever run **once per user per process lifetime**, never again — defeating the entire point of §7.1's per-call resolution. **Resolution:** M22.6 changes all three caching call sites to resolve via `ModelRouter` fresh on every real call (matching `response_drafting.py`'s existing, already-correct shape), not just to thread `principal` through a still-cached `build_provider()` result.

**0.2 — Budget-awareness is a seam in M22.6, not a mechanism.** §22.1 lists M22.6's objective as "health/budget-aware fallback," but `usage_meter.py` (the actual budget/ceiling data) is explicitly an M22.7 file, and M22.7's own entry describes wiring "budget pre-flight" into `model_router.py` as *its* work. There is no usage data to check yet. **Resolution:** `ModelRouter.resolve()`'s decision pipeline includes a budget-check step in the exact position §7.1 specifies (between health and user fallback order), implemented in M22.6 as a step that always passes (no ceiling data exists, so nothing can be over budget) — a named, tested no-op, not an omitted step — so M22.7 can slot in the real check later without restructuring the pipeline or its tests. No `usage_meter.py`, no budget config, no ceiling logic is built in M22.6; inventing any of that now would be exactly the "unconsumed configuration surface" the architecture doc repeatedly warns against (§6.5, §21).

If the User wants a different resolution to either point, say so at ACCEPT; otherwise both are treated as accepted defaults.

## §1. Objective

Per URI_M22_ARCHITECTURE.md §7, §9, §22.1: a deterministic `ModelRouter` that resolves which provider/model answers a given role for a given principal, with health-tracked fallback and a reserved (not-yet-active) budget-check seam, ending in a mandatory "no reachable model" degrade state that never blocks deterministic capabilities. Auth failures stop the chain rather than silently trying a different provider/key.

## §3. Scope — file by file

**NEW `uri_core/core/model_router.py`**
- `ProviderPlan` (dataclass, frozen): `provider_id`, `model`, `config: ModelProviderConfig`, `fallback_chain: List[str]` (provider_ids tried, in order, for observability — see §6 acceptance criterion on "which model actually answered").
- `ModelRouter.resolve(role: str, principal: Optional[PrincipalContext]) -> ProviderPlan` — pure decision function, deterministic given its inputs. Pipeline, in the exact order §7.1 specifies:
  1. User's configured primary for `role` (from `ProviderConfigStore`/`model_roles.json`, exactly as `build_provider` already resolves it).
  2. Health check: `ProviderHealthTracker` (new, in-memory, per-process) — `(provider_id, model)` marked unhealthy for a short cooldown (fixed constant, e.g. 60s) after a `ProviderUnavailableError`/`ProviderTimeoutError`/`ModelNotFoundError`; **never marked unhealthy on `ProviderAuthenticationError`** (§5.1) since that's a config problem, not a backend outage, and sticking it in the same cooldown table would incorrectly let it "expire" and get silently retried.
  3. Budget pre-flight seam (§0.2) — always passes in M22.6.
  4. User's declared fallback order (list of provider_ids in per-user config; absent means no configured fallback).
  5. Install default (`ollama`, always permitted — the packaged zero-config path).
  6. Any other healthy local (`adapter == "ollama"`) provider.
  7. **Degrade** — `ProviderPlan` with `provider_id=None` (see `attempt(...)` below), meaning §9's degrade path is entered.
- `ModelRouter.attempt(role, principal, complete_kwargs) -> ModelResponse` — the actual per-call entry point the four leaf modules use instead of calling `build_provider(...).complete(...)` directly: walks `resolve()`'s chain, constructs each candidate via `build_provider(role_override_provider_id, principal)` (small internal extension to `build_provider` — see below), calls `.complete(**complete_kwargs)`, catches `ProviderTimeoutError`/`ProviderUnavailableError`/`ModelNotFoundError` and advances to the next candidate (marking health as it goes), but **`ProviderAuthenticationError` propagates immediately, uncaught** — this is the literal mechanism behind §5.1/§7.2's "auth failure stops, does not fall back." Raises a new `AllProvidersUnreachableError` (defined here) when the chain is exhausted with no success — this is what the four leaf modules catch to enter their own degrade behavior (§9).

**MODIFY `uri_core/config/model_roles.py`**
- Small, additive extension: `build_provider` gains an internal way for `ModelRouter` to force a specific candidate `provider_id` from the chain (rather than always reading the role's single configured provider) — implemented as an optional `provider_id_override: Optional[str] = None` keyword-only parameter, defaulting to current behavior when omitted (every existing call site — all four leaf modules' pre-M22.6 shape, every test — is unaffected). `UnknownModelProviderError` behavior is unchanged.

**MODIFY the three caching leaf modules** (§0.1) — `provider_semantic_interpreter.py`, `model_reasoning_adapter.py`, `document_composer.py`:
- Remove the construction-time/lazy-cache `build_provider(...)` call. Each module's real per-call method (`interpret()`, `__call__()`, `compose()`) instead calls `ModelRouter.attempt(role, principal, ...)`, passing through whatever `principal` its own caller now supplies (see below). The `provider: Optional[ModelProvider] = None` constructor parameter is **kept unchanged** for existing tests that inject a fake provider directly — when a caller passes one explicitly, it is used as-is with no router involved, exactly like today (zero-behavior-change for every test that already does this).
- `AllProvidersUnreachableError` is caught at each of these three call sites and turned into that module's own existing "unavailable" contract (e.g. `ProviderSemanticInterpreter.interpret()` raising the same `ValueError`/contract it already uses for a malformed response, `DocumentComposer.compose()` returning `composed_by: "fallback"` — its own module docstring already describes this exact fallback-on-unreachable path, just triggered by a new exception type instead of the old provider's own raised error).

**MODIFY `response_drafting.py`**
- `draft_response()` already resolves fresh per call (§0.1) — only the resolution line itself changes, from `provider = provider or build_provider(ROLE_DRAFTING)` to routing through `ModelRouter.attempt(ROLE_DRAFTING, principal, ...)` when no explicit `provider` override is given and a `principal` is available; `ResponseDraftingError` (already the module's own catch-all) absorbs `AllProvidersUnreachableError` exactly as it absorbs any other exception from `provider.complete()` today — **no new except-clause is needed**, confirmed by reading the existing `try/except Exception as exc: raise ResponseDraftingError(...) from exc` block.

**MODIFY the four leaf modules' own callers** to thread `principal` down to them (the actual plumbing that makes the principal available at the point `ModelRouter.attempt` needs it):
- `orchestrator.py` already carries `self.principal`/per-session `principal` (M22.4 work, already in the tree) — confirmed by reading the current diff: `_process_user_input_core` already resolves a `principal` local variable from the session or `self.principal`. M22.6 adds passing that same already-resolved `principal` into `self.semantic_interpreter.interpret(...)` and `self.model_reasoning_gateway`'s callable, and `document_composer.compose(...)`'s call site — **small, additive parameter threading only, not new logic.** This does not grow `orchestrator.py`'s line count in any meaningful way (a handful of `principal=principal` keyword arguments at existing call sites) and does not add any provider-selection *logic* to `orchestrator.py` itself, preserving §17.2's "zero required changes" in spirit (`wc -l` is still checked as an explicit acceptance criterion, see §6, to keep this honest rather than asserted).

## §5. Security Considerations

**5.1 — Auth failure stops, never falls back (the load-bearing rule of this milestone).** `ModelRouter.attempt()` must let `ProviderAuthenticationError` propagate uncaught out of the fallback loop — it is not one of the caught-and-advance exception types. A broken/revoked key must surface as an explicit, honest error to the caller, never silently retry a different provider (which could spend a different provider's quota without the user knowing why — architecture doc §7.2) and never mark the provider merely "unhealthy" in the cooldown tracker (§3's health tracker explicitly excludes it), since an expired cooldown would let the *same* broken key be silently retried later.

**5.2 — No new secret-handling surface.** `ModelRouter` never itself touches `ProviderKeyStore` — it calls `build_provider(role, principal, provider_id_override=...)`, which is already the sole permitted caller of `ProviderKeyStore.get_key_for_use()` (M22.5 invariant #4, unchanged, re-verified by the existing `test_provider_keys_boundary.py` continuing to pass unmodified).

**5.3 — Health/fallback decisions carry no key material.** `ProviderHealthTracker`'s in-memory state is keyed by `(provider_id, model)` only — never a user_id-scoped structure holding anything sensitive, and never persisted to disk (process-memory only, explicitly, like `AuthSessionStore` pre-M22.2 — but here that's the correct, intentional design, not a gap: health is inherently transient, per-process operational state, not a durability requirement).

**5.4 — Degrade is honest, not silent.** Per §9: when `AllProvidersUnreachableError` is raised, every caller surfaces the real reason (no provider configured / all unhealthy / auth failure occurred) rather than a generic failure — this is a UX/observability requirement more than a security one, but it's the direct fix-verification for §9's "reported honestly to the user" rule.

## §6. Acceptance Criteria

1. A forced-unhealthy primary provider correctly falls back to the next candidate in the chain, and the caller can determine which provider/model actually answered (via `ProviderPlan.fallback_chain` or the equivalent surfaced field).
2. A `ProviderAuthenticationError` from any candidate immediately propagates — it is never caught and does not advance to the next candidate in the fallback chain.
3. With every configured provider forced unreachable, `AllProvidersUnreachableError` is raised, and the deterministic-capability test suite (approve/reject, list tasks, read history, list files, list memory, view usage) passes unchanged — none of these call a model or are gated by `ModelRouter`'s outcome.
4. `UnknownModelProviderError` is still raised for an unregistered provider id, unchanged from M21/M22.5.
5. `wc -l uri_core/core/orchestrator.py` does not increase (invariant #11, architecture doc §19.4) — measured exactly, not estimated.
6. Invariant #2 (§19.4): `model_router.py` never imports `approval_gate`/`approval_store`/`dispatcher`/`capability_registry`.
7. The three previously construction-time-caching leaf modules (`provider_semantic_interpreter.py`, `model_reasoning_adapter.py`, `document_composer.py`) resolve a fresh `ModelRouter.attempt()` call per real invocation, not a cached provider from `__init__`/first-call — verified by a test that changes health state between two calls on the same long-lived instance and observes the routing decision actually change.
8. Existing M21/M22.5 regression tests for all four leaf modules (`test_provider_semantic_interpreter.py`, `test_orchestrator_semantic_interpreter_provider.py`, `test_m21_provider_config.py`, `test_provider_registry_catalogue.py`, etc.) pass unmodified when a caller injects an explicit `provider=` override — confirming the router is bypassed cleanly, not merely overridden.
9. Full existing regression suite (1,318 Python tests as of the M22.5 baseline, plus new M22.6 tests) passes; Flutter suite unaffected since §8 below declares `UI IMPACT: NONE`.

## §8. UI Impact

**UI IMPACT: NONE.**

Justification: `ModelRouter` is a pure backend decision layer with no new user-facing data or action. It does not add, remove, or change any HTTP endpoint (`/providers`, `/providers/keys`, `/providers/config` from M22.5 are untouched), any request/response shape, or any client-visible state. The Flutter client already displays per-provider `available`/`configured` status from `GET /providers` (M22.5); this milestone changes *which provider actually answers a given call* and *how gracefully it degrades*, which surfaces to the user only through the pre-existing `/capabilities` self-knowledge and pre-existing "the Brain is unavailable" narrative paths already exercised by §9's existing test pattern — no new screen, dialog, or client method is required. If a future milestone wants to surface "which model actually answered this turn" or fallback history to the user, that is new UI scope belonging to that milestone, not implied by M22.6's backend routing work.

## §9. orchestrator.py Line-Count Impact

**Near-zero, and measured, not assumed.** The only change inside `orchestrator.py` is passing the `principal` value it already resolves (M22.4 work, already in the tree) as an additional keyword argument at 2-3 existing call sites into `self.semantic_interpreter`/`self.model_reasoning_gateway`/document-composition call points — no new conditional logic, no new provider-selection code. `wc -l uri_core/core/orchestrator.py` is measured before and after as acceptance criterion 5; if Gemma's implementation would require it to grow, that is a signal the threading was done in the wrong layer and must be pushed down into the leaf modules instead, not accepted as "small enough."
