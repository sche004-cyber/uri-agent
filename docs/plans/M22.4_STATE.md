### Round 1 — NOT VERIFIED (2026-09-11, Claude) — superseded by Round 2 above

- **Decision:** NOT VERIFIED
- **Basis:** Independently inspected the actual diffs against baseline
  `8acbad5`, not the reports' text alone (full basis recorded at the time
  this round ran; condensed here to the confirmed gaps it produced).
- **Remaining gaps (as found in Round 1):**
  1. **Confirmed, blocking:** With no `principal` supplied,
     `CapabilityResolver.is_allowed` computes `user_id = None`, and
     `CapabilityGrantsStore.get_grants(None, registry_ceiling_ids=...)`
     returns `set(registry_ceiling_ids)` — the **full registry ceiling**
     (`capability_resolver.py` lines ~115-116: `if not user_id: return
     set(registry_ceiling_ids)...`). So every real, live execution
     through the orchestrator today resolves as "allowed" regardless of
     that user's actual stored grants — **the new authoritative check is
     unreachable with a real value in production and enforces nothing
     for an actual user turn.** This directly contradicts Plan §5.1
     point 1 ("an attacker... that never consults `/capabilities` at all
     still cannot execute an ungranted capability") and Acceptance
     Criterion §6.2, which is only true when a caller manually supplies
     `principal=` — which no real call site does.
  2. **Related design gap, same root cause:** `get_grants`'s "no
     `user_id` → full ceiling" branch conflates two different cases that
     should not be conflated: (a) a *known* user with no grants record
     yet (intentional, zero-behaviour-change migration default — correct
     to fail open here) vs. (b) *no principal identified at all* (should
     fail closed, not open — an anonymous/unauthenticated caller should
     never silently receive the full registry). Fixing gap 1 by wiring
     `principal` through the real call sites does not by itself fix this
     — the resolver should also be able to distinguish "authenticated
     user, no record" from "no authentication context at all."
  3. Antigravity's audit report's "Outstanding Gaps: None" did not catch
     this — the audit's "Test Sufficiency Assessment" counted assertions
     in the new test files but did not check whether those tests
     exercise the real call path. Re-running the existing test suite
     again will not surface this; a new test is needed that calls
     `execute_tool` exactly the way `orchestrator.py`/
     `workflow_capability_router.py` actually call it (i.e. without
     manually injecting `principal`) using a real multi-user fixture, and
     asserts the per-user restriction still holds — proving this end to
     end rather than only at the unit level.
  4. **Unrelated to M22.4 but flagged while inspecting `git status`:**
     `scripts/dev_workflow/` and `tests/dev_workflow/` remain untracked
     in the working tree. These are not part of the M22.4 plan's scope
     (they were not introduced by this milestone) and the Antigravity
     Audit Report's "Evidence" line cites "47/47 dev_workflow security
     tests passing" from `tests/dev_workflow` as if it were part of this
     milestone's verification — it is not in scope and should not be
     cited as M22.4 evidence. This does not by itself block M22.4 (it
     doesn't touch M22.4's own acceptance criteria), but it should not be
     commingled with M22.4's evidence again, and its presence in the
     working tree is a separate, already-flagged-to-the-User item from
     an earlier, unauthorized peer-session write — not something
     Antigravity should build on or extend under cover of this
     milestone.

  **Next step:** return to `FIXING`. Antigravity should wire the current
  turn's real `PrincipalContext` through to `self.approval_gate.
  execute_tool(...)` at all three real call sites, reconsider the
